# weilo-agents: design

The full documentation, with diagrams, is in HTML: start at [index.html](index.html). This file keeps the dense reference tables.

A chat app for the pi coding agent. Pi runs in a Docker container; a small daemon in that
container serves the UI and runs pi. All user data is one host folder, `~/.weilo-agents`.

## Decisions

| Topic | Decision |
|---|---|
| Runtime | Docker only (host mode later; the daemon has no Docker code). |
| Daemon | Inside the container, as its main process. No Docker socket. |
| Data | `~/.weilo-agents` mounted at `/home/node/.pi`. Copy it to move machines. |
| Providers | No setup page. No provider yet: composer disabled, "Add a provider" opens Settings. Keys only. The agent form picks the first connected provider, but the model is always yours to choose. A connected provider has Models and Edit key (the same field replaces the key). Settings lists the connected providers first (In use), then the rest (Add another). |
| Agents | Lean profiles: a folder with one file, `agent.json`, which holds the instructions too. Shared pi config. Each agent is one continuous conversation (messenger style): no chat list, no titles. Two kinds: regular (the default) and isolated (Isolated agents below); `isolated` and `trusted` are set only in the app. |
| Isolated agents | An agent with only its own folder (`isolated: true` in its profile; Edit agent > Access > Isolated, shown with an Isolated tag). It runs in the sandbox (Sandbox below), not in the app's container: it cannot see the workspace, `agent/`, another agent's folder or chat, the keys, the app's processes or another agent's. Its folder is `isolated/<folder>/` (its user's and its own group's, 2775 with setgid, umask 002: it and the plugins it uses write there; `isolated/` is 0750 root and `agents`, so every regular agent, and the regular agents' plugins, read it and cannot change it: what it does is part of what they know of your work, and nothing they do changes it), its chat `isolated-sessions/<id>/`, its HOME `isolated-homes/<folder>/`. The daemon reads its chat for search, `fetch_knowledge` and the curator, and the curator files what it writes in `shared/` (Memory below); both come marked as an isolated agent's report. It has no shared `USER.md` or `MEMORY.md`, no `memory`, `fetch_knowledge`, `skill`, `manage_settings` or `ask_agent` tool (not in its `--tools`, and the routes refuse it: `mayCall` in `agents.mjs`), keeps notes as files in its folder, and its scratch is its own `/tmp`. The browser (shared sign-ins) is turned off when it becomes isolated, and its route is refused while off; turning it on is the user's, or a `manage_agents` request the user approves; its actions stay. Making an agent isolated, or regular again, stops its pi (no pi starts meanwhile: `holding` in `runner.mjs`), moves its folder, chat and HOME, and gives what is in its folder to its user, in its folder's new group. |
| Sandbox | A second container from the same image, `weilo-sandbox` (`node /app/sandbox/server.mjs`), for isolated agents and the plugins they use. It mounts only `isolated/`, `isolated-sessions/`, `isolated-homes/` and, read only, `agent/skills/` and `agent/extensions/`, and holds no key. The app asks it over `/run/weilo-sandbox/ctl.sock` (the `sandbox` volume, root's alone on both sides) to start a program: a spec of the user, the command, its folder, its environment, its umask, the places it may have and the files of its pi folder (`sandbox/client.mjs`; `sandbox/spec.mjs` refuses root, any place outside those folders, any link, and files outside `/var/lib/weilo`). It starts each one with `unshare` in namespaces of its own (pid, mount, ipc, uts) under `tini`; `sandbox/enter.mjs`, as root in them, puts empty folders over the data folder, `/var/lib/weilo`, the sandbox's socket, `/tmp` and `/dev/shm`, gives back only the program's places (read only where asked), writes its pi folder, and starts it with `setpriv` as its user with no capability. So a program sees its own processes, its own `/tmp` and only its folder. Its output comes back framed (stdout, stderr, exit: `sandbox/frames.mjs`); when the app hangs up, its stdin ends and it is killed 5 seconds later with all it started. Agents reach the app as `127.0.0.1:3210`, which the sandbox forwards to the app's socket for it. The kernel is the host's, as for every container; `WEILO_SANDBOX_RUNTIME=runsc` runs the sandbox on gVisor, a kernel of its own, where gVisor is installed. If it cannot make namespaces it starts nothing (fail closed), and Settings > Devices says so. |
| Network | Port on `127.0.0.1` only, plus `Host`, `Origin` and `Sec-Fetch-Site` checks; no other site may frame the app. Every API call also needs a paired device's cookie or an agent's key (Access below). The sandbox has a Docker network of its own (the internet, not the app); it reaches the app only through a socket in the `sandbox` volume (`/run/weilo-sandbox/api.sock`), on which the app takes nothing but isolated agents' keys, and an isolated agent's key works nowhere else. |
| User | The daemon runs as root (the image sets no `USER`) and starts every other program as a user of its own (see Users). Agent installs (`npm -g`, `pip --user`) persist in volume `tools`. `start.sh` makes `~/.weilo-agents` first, so Docker does not make it as root. |
| Names | Stack `weilo-agents`, container `weilo-core`, image `ghcr.io/shyam1203/weilo-agents:<version>`. |
| Versions | One `VERSION` file (SemVer). The image build takes `VERSION` and `COMMIT` as build arguments and keeps them as `WEILO_VERSION` and `WEILO_COMMIT` (`daemon/version.mjs`, which also reads pi's version from its package; `GET /api/version`, Settings > General) and as OCI labels. pi and `playwright-core` are installed with `npm ci` from `image/pi/package-lock.json` (versions and hashes), and the base image is pinned by digest; every GitHub Action is pinned to a commit SHA; Dependabot proposes updates to all of them, but not a new major of the `node` image or `@types/node` (Node 22 LTS is the runtime). A `v*` tag runs `.github/workflows/release.yml`: it checks and tests, builds the amd64 image, starts it with compose and runs the same smoke test as CI (`.github/scripts/smoke.sh`: `/api/health`, the sandbox makes namespaces, the UI is sent compressed), builds arm64 and checks `node:sqlite`, the daemon and pi are in it, and only then builds both with provenance and an SBOM, pushes the image and publishes a release with a zip (`compose.yaml`, start and update scripts, `VERSION`). The start scripts set `WEILO_VERSION` from `VERSION` and pull that image; if the pull fails they start the copy already on the computer, else build it when `image/Dockerfile` is there (a clone, not the release zip), else stop and say to check the internet connection. The data folder has `weilo.json` `{dataVersion, version}` (`daemon/migrate.mjs`): older data is brought up by ordered steps at start, newer data stops the start with a message. See `docs/RELEASING.md`. |
| Hardening | The app's container drops NET_RAW, NET_ADMIN, MKNOD, AUDIT_WRITE, SYS_CHROOT, SETFCAP and NET_BIND_SERVICE, with `no-new-privileges`. The sandbox drops every capability but CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, SETPCAP, KILL and SYS_ADMIN (what making namespaces and starting a program as another user take), with `no-new-privileges` and `apparmor:unconfined` (AppArmor's Docker profile forbids mounts); every program it starts has no capability at all. Both have a healthcheck (`GET /api/health`; the sandbox's socket), `restart: unless-stopped`, and limits on processes and memory (`pids_limit`, `mem_limit`: the app 4096 and 8 GB, the sandbox 2048 and 4 GB; `WEILO_CORE_PIDS`, `WEILO_CORE_MEMORY`, `WEILO_SANDBOX_PIDS`, `WEILO_SANDBOX_MEMORY` change them), so a fork bomb or a runaway program in one stops at its limit. |
| Attachments | Images go to pi as image blocks. Other files are saved to `uploads/` in the agent's folder and named in the message (a path from there). |
| Thinking | Optional per agent (`off` to `max`); empty means pi's default. |
| Launch | `start.cmd` (Windows) and `start.sh` (macOS, Linux) pull the image (if that fails: start the copy already on the computer, or build it when `image/Dockerfile` is there, or say to check the internet connection), run `docker compose up -d`, wait up to 90 seconds for the app, and open the browser at a pairing link. |
| Models | Settings lists each provider's models; the ones switched on are pi's `enabledModels` (`settings.json`) and are all an agent's form offers. None switched on means all. |
| Skills | Pi's own `agent/skills/`, added by uploading a `.zip` (no links inside) or `SKILL.md`. An agent's profile lists the ones it uses; pi starts with `--no-skills --skill <path>` for each. An agent saves one with the `skill` tool (`POST /api/agents/:id/skill`, `planSkill` and `saveSkill` in `settings/skills.mjs`): the daemon first asks the user in its chat (`askUser`: the name, the description, the instructions in full, at most 16000 characters, and whether it changes an existing skill and which other agents use it), and only on Save it writes `SKILL.md`, turns it on for that agent and restarts its pi. A no is final unless the user asks again. A regular agent's house rules (`agents/workspace.mjs`) tell it to offer once, after a task of many steps or a tricky one, to save how it did it as a skill. |
| Shortcuts | Typing "/" in the message box lists the agent's skills (pi's `get_commands`, source `skill`) and plugins. A skill inserts `/skill:name`, which pi expands; a plugin inserts a starter sentence. Chats and the agent list show the typed `/name`, not the expansion. Pi's own terminal commands, prompt templates and extension commands are not offered. |
| Plugins | MCP servers in pi's `agent/mcp.json`, added in the UI as a command or a web address. A web plugin that answers 401 shows "Needs sign-in" (`pluginStatus`); Sign in runs MCP's OAuth (`settings/oauth.mjs`): the protected resource metadata (RFC 9728) names the authorization server, whose metadata (RFC 8414) gives the endpoints; the app registers itself (RFC 7591, a public client, kept per redirect address) and signs in with PKCE and `resource`. The callback, `/api/plugins/oauth/callback`, is the one API path a link from another site may open (`guard`), and it needs no cookie: the one-time state (15 minutes) stands for the device that started it. The tokens stay in the plugin's `oauth` in `mcp.json` (never in an agent's copy, `piPlugins`); the proxy adds the access token, renewed with the refresh token a minute before it runs out. A profile lists the ones an agent uses; pi gets them in its `--tools` allowlist, and `--no-mcp` when there are none. Secrets stay in `mcp.json`. |
| Extensions | Everything an agent can do beyond chat is a pi extension: a folder with a `weilo.json` (`apiVersion` 1, `name`, `description`, `entry`, `tools`; optional `title`). Pi loads each with `-e <entry>` and the daemon adds its `tools` to `--tools` (pi hides a tool the allowlist does not name). Two kinds, listed together by `GET /api/extensions` (`builtin` tells them apart). **Bundled** ones are the `extension/` folder of `browser/` and `actions/` in the daemon (in the image under `/app`): an agent has them unless its profile's `disabled` list names them (Edit agent: Built-in extensions, a switch each), and they cannot be deleted. Each calls only the daemon's HTTP API (through the shared `tool.mjs`), so another extension can replace it: add one that declares the same tool, and turn the bundled one off for that agent. With both on, saving the agent is refused (two extensions add one tool). **Added** ones are uploaded as a `.zip` (at its top, or in the one folder that wraps it), unpacked with the skills' checks (no links, size limit) into `agent/extensions/<name>/`; a tool name pi, the chat or memory uses (`show`, `ask`, `skill`, `manage_agents`, `manage_settings`, `memory`, `fetch_knowledge`) is refused (and left out if an older one declares it), so is an entry outside the folder or a name a bundled one has. Adding asks first: the code runs with the agent's rights and can read the keys. An agent's profile lists the added ones it uses (`extensions`). Nothing else in `agent/extensions/` loads (`-ne`). Memory is not switchable: every regular agent has its tools, notes and a place in the curator's reading (`memory/extension.mjs`, loaded with `weilo.mjs`), because any agent can search every chat and read the memory files anyway. An agent's instructions say whether it should use memory. Not changed by a switch: actions already set to run by themselves keep running, and other agents' `fetch_knowledge` still searches this agent's chat. The UI's browser and actions panels show "turned off" for an agent that has the extension off. Not done: pages or blocks drawn by an extension in the chat. |
| Always allow | The approvals of `ask_agent` (per other agent, `ask:<id>`), `skill`, `action` (create and update) and `manage_settings` offer "Always allow" (`agents/approve.mjs`): it counts as yes and adds the rule to the profile's `allow`, which only the user changes (Edit agent > Access, or the API; `manage_agents` refuses it). An allowed request goes ahead and the chat shows a line (the tool result's `details.note`). Making or changing other agents always asks. |
| Keys | The `key` tool (every agent, isolated ones too): `ask` shows a protected field in the chat (`askUser` with `secret`: the answer goes to the daemon only, and the audit says "(saved)"), and the daemon keeps the value in `agent/keys.json` (root's, 0600) by agent and name, with its https origin and how it is sent (bearer, a named header, or basic). `use` makes the request for the agent: only to that exact origin, no redirects followed, 30 seconds, 1 MB read, 20,000 characters back, with the value and its encodings taken out. The value is never in the agent's shell, files or chat. |
| Teaching | Browser panel > Show how takes over the agent's window and records (`startTeaching` in `browser/browser.mjs`): each tab gets an init script and a page binding that report clicks, changes and Enter (no password or secret-looking value), and the app notes the pages opened (a redirect keeps only the last). Done (`finishTeaching`, with what the user calls it) gives the window back and sends the numbered steps to the agent, asking it to save a skill (the usual skill approval). Give back or Cancel drops the recording. |
| Waiting questions | A question in the chat (`askUser`, or pi's `ask`) notifies again after an hour ("Still waiting for you") and closes after a day as if skipped (`ASK_REMIND_MS`, `ASK_CLOSE_MS`). |
| Quiet checks | An action that ran by itself tells the agent to reply only `NOTHING_NEW` when it found nothing worth telling: then no notification, and the chat folds the run into one line. A script action returns null for the same. |
| Access | Every agent has the same pi tools (`read`, `bash`, `edit`, `write`), as a Linux user of its own (Users below): a regular agent shares the workspace, the installed tools and the skills with the other regular agents, and reads (not changes) isolated agents' folders; an isolated agent has only its own folder, in the sandbox. No agent can read the keys of a provider with a key, the plugins' secrets, the paired devices, the vault, the browser's profile or another agent's chat. The daemon holds the keys and adds them to the agent's requests (Keys below), and checks every tool route an agent calls (`mayCall`). |
| Users | The daemon is root and runs nothing else as root (`users.mjs`; `setpriv` drops every capability for good). Each agent is a user of its own (`uid` in its profile, from 2001; never given twice: `weilo.json` keeps the highest, `lastUid`, so a new agent never owns what a deleted one left), a regular one in the group `agents` (2000), an isolated one in none but its own (it runs in the sandbox); the browser (Xvnc, openbox, Chromium, started on first use) runs as `node` (1000), the curator as 1100, each plugin that runs as a program for a regular agent as a user of its own (300000 + n, n given once per plugin name and kept in `agent/plugin-users.json`; `pluginUser` in `users.mjs`), in `agents`, so it reaches the workspace and reads the isolated folders but not another plugin's environment or files, an isolated agent's in the sandbox as its uid + 100000, in its group. `agent/` is root's, but for what a regular agent's pi reads (its profile, `USER.md`, `MEMORY.md`, the skills, the extensions: group-readable; the skills group-writable, the extensions not). `workspace/` and each agent's folder in it are the group's (setgid, umask 007); `workspace/` and `skills/` are 3770 (sticky too), so an agent cannot rename or delete another agent's folder or a skill folder it does not own at their top level; `isolated/` is root's and the group's (0750), each folder in it its agent's and its agent's group's (2775: the group `agents` reads it as others; `secure()` sets it at every start, and hands the contents of one still in another group to its agent once); `isolated-sessions/` and `isolated-homes/` are root's (0711); `agent/sessions/<id>/`, `isolated-sessions/<id>/`, `homes/<folder>/` and `isolated-homes/<folder>/` (HOME) and `/tmp/weilo/<id>/` (scratch) are the agent's own; `knowledge/` the curator's. Root sets an owner through the folder itself, never through a link an agent put in its place, and keeps a pi's folder its own until all of it is written: `tree()` opens the folder with `O_NOFOLLOW` (`inFolder` in `users.mjs`) and runs `chown`, `chmod` and `find` on `/proc/<pid>/fd/<n>/`, so a folder an agent swapped for a link is left alone; `move()` (`agents.mjs`) refuses to move an agent's folder that is a link; an approved skill's `SKILL.md` is written through the opened folder with `O_NOFOLLOW` (a skill folder or `SKILL.md` that is a link: 409). `secure()` sets the top of each place at every start; data version 3 (`migrate.mjs`) handed an older folder's files to their owners once; data version 4 marked every agent regular and not trusted, and set `lastUid` from the profiles and the owners of the files; data version 5 moved isolated agents' HOMEs to `isolated-homes/` and made their folders readable (not writable) for the regular agents. **PATH:** root starts every program by its full path (`BIN` in `config.mjs`), and everything it starts gets a PATH of root's folders only (`SYSTEM_PATH`), since the image puts `~/.local/bin`, which agents can change, first. A regular agent's pi and plugins get the shared tools after root's folders; an isolated agent's get its own (`.local` in its HOME). **Environment:** a regular agent's pi, and a plugin's status check (`pi mcp list`), get only an allow-list of the daemon's environment (`passedOn` in `users.mjs`: `LANG`, `LC_*`, `TZ`, `TERM`, `NODE_PATH`, `PIP_BREAK_SYSTEM_PACKAGES`, `WEILO_VERSION`, `WEILO_COMMIT`, the proxy variables and the CA-certificate ones), never all of it; an isolated agent's gets only what the app names. |
| Keys | No key of a provider or a plugin is in reach of a pi. Each pi starts with a folder of its own (`PI_CODING_AGENT_DIR` = `/var/lib/weilo/pi/<id>/`, its user's alone, made again at every start by `agents/pidir.mjs`; an isolated agent's is written by the sandbox, from the files the app sends): `settings.json`, a `models.json` with only its model's provider, an `mcp.json` with only its plugins, and an isolated agent's profile. Every provider points at `/api/model-proxy/<provider>` (`baseUrl`) with an `apiKey` made from the pi's own key (`http/access.mjs`): the key itself for a provider with an API key; for one signed in with an account, a placeholder of the shape pi reads (`placeholderFor` in `gateway/models.mjs`): Anthropic `sk-ant-oat01-<key>`, ChatGPT an unsigned JWT that carries only the real `chatgpt_account_id` and has the key as its signature part, GitHub Copilot `tid=weilo;proxy-ep=…;weilo=<key>`. `settings.json` sets `transport: "sse"`, so pi opens no WebSocket around the proxy. With a ChatGPT sign-in, the provider also gets `compat` flags so pi leaves out the request fields that sign-in refuses (pi would only know to from the real address). A new key, a removed one or a finished sign-in restarts the agents (each when its run ends), since the placeholder is chosen when a pi starts. The daemon finds the agent's key anywhere in `Authorization`, `x-api-key`, `x-goog-api-key`, `api-key` or `?key=`, checks the provider is its model's, swaps the whole token that holds the key for the real one in those places only and drops any other header that holds the key, so a provider that repeats a header back never shows the real token (`keyedHeaders`, `swapKey`; an account's access token renewed to have at least 5 minutes left, by `getAuth`, and sent to the address the sign-in names, if any) and streams the request on (`gateway/forward.mjs`). pi sends all of a provider's models to one address, so the daemon picks the provider's address for the API the path names (OpenRouter has two). No account token, access or refresh, reaches a pi. A plugin on the web points at `/api/plugin-proxy/<name>` with the pi's key, which the daemon swaps for the plugin's headers; one that runs as a program is `node /app/gateway/pipe.mjs <name>`, a pipe (an HTTP upgrade to `/api/plugin-pipe/<name>`) to the daemon, which starts the program with its secrets in its environment (`gateway/plugins.mjs`), never as an agent and never in a folder an agent writes (a planted `.npmrc` or module would load there; the agent's folder is `WEILO_FOLDER`): a regular agent's as that plugin's own user, with HOME `/var/lib/weilo/pi/plugins/<name>/` (0700, that user's; `plugins/` itself root's, 0711), in an empty folder of root's (`/var/lib/weilo/pi/plugins-cwd`), an isolated agent's in the sandbox as a user of its own (the agent's uid + 100000, in the agent's group), with only the agent's folder and its own `/tmp`. Every agent reaches only its own plugins. The curator's pi gets the same, for the curator's model. |
| Workspace | One folder, `workspace/`, which the user browses. Each regular agent has a home in it, `workspace/<folder>/` (`folder` in its profile: its name as a slug, made unique against what is in the workspace, fixed when the agent is made so a rename keeps its chat's paths), and pi runs there; the rest of the workspace and the container stay open to it, so this is order, not a fence. Each agent gets house rules (`agents/workspace.mjs`, appended to its system prompt): its work in its folder, a folder per task, clear names, no leftover copies, the rest shared but never another's files unless asked; pi also reads any `AGENTS.md` in its folder and above. Each agent also has a scratch folder of its own outside it, `/tmp/weilo/<agent>` (`WEILO_SCRATCH`), for downloaded pages, one-off scripts and raw data; it is emptied when the agent goes idle, and all of them when the daemon starts. Deleting an agent keeps its folder unless the user ticks the box. Files from before agents had folders stay at the top of the workspace, shared. An isolated agent's folder is outside the workspace (`isolated/<folder>/`), and its rules say it has only that folder (keep notes there; write in `shared/` what the user's other agents should learn; scratch in its own `/tmp`; ask with `manage_agents` for a skill, plugin or extension). |
| Show | `daemon/weilo.mjs` is a pi extension (`-e`) that gives every agent the chat's own tools, `show` and `ask`. `show` is: a list of blocks (text, table, metrics, cards, chart, buttons, file, page). The UI draws them from the tool call in the saved conversation (`blockData.ts`/`ShowBlocks.tsx`); no AG-UI layer, pi's events are enough. Cards and buttons send a message as the user's reply; the chosen one stays marked. Unknown or malformed blocks are dropped. |
| Files | `GET /api/agents/:id/files/<path>` serves a regular file, looked for from the agent's folder first and then from the top of the workspace (paths in older chats); a full path is taken as it is. It opens the file first (a FIFO without blocking) and checks the opened file's real path (`/proc/self/fd/<n>`) against the roots, so a folder swapped for a link mid-request is refused, then streams from that same handle. A regular agent's chat shows files in `workspace/` and `isolated/`, an isolated agent's only those in its own folder (`filesOf`). Pictures show inline; everything else downloads, with `Content-Security-Policy: sandbox`. With `?view=1` (the chat's preview) a text file is sent as plain text and a PDF inline (a PDF is not sandboxed: the browser's viewer does not run in one). The chat previews (`features/files/`) pictures, PDFs, Markdown, CSV/TSV (a table), JSON, HTML (the same sandboxed frame as a `page` block) and text or code; other files only download. A file block has Preview and Download; an agent's text that names a file as inline code, with its full path in the workspace or an isolated agent's folder (`/home/node/.pi/workspace/…`, `/home/node/.pi/isolated/…`) or a path from the agent's folder (`notes/plan.md`: a folder, and a file kind the preview shows), becomes a button that opens the preview. Another long path (the agent's own files) shows as its file name; a tap shows all of it. |
| App | `GET /api/version`; `GET`/`PUT /api/update` (`update.mjs`: the newest GitHub release, asked at most every 6 hours, only if `checkUpdates` in `weilo.json` is not false and not for a build made without a version (`dev`); the sidebar and Settings > General say when one exists, and the user runs `update.cmd` / `update.sh`, which download the newest release zip over the folder and run the start script); `POST /api/contact` (`contact.mjs`: Contact us, from the mail button beside Settings, forwards name, email and message with the app version to weilo-api's `POST /public/contact`; nothing from the chats). |
| Pages | A `page` block is agent-written HTML in an iframe with `sandbox="allow-scripts"` (empty origin: no access to the app, API or storage), a content policy that allows https only, and the app's own `frame-src about:` so the frame can't navigate. It talks to the chat through its height and `weilo.reply(text)`, which the app takes only during a user click in the frame. The app tells it the room it has and the app's look: `weilo.screen` (`{width, phone, dark, colors}`), the colors as `--weilo-bg`, `--weilo-card`, `--weilo-text`, `--weilo-muted`, `--weilo-line`, `--weilo-good` and `--weilo-bad`, and a `weilo:screen` event when its width or the theme changes; the agent is told to wrap, avoid fixed widths and use those colors. Text blocks follow the replies' Markdown rules (remote images show as links). |
| Ask | The same extension has an `ask` tool: a question with options (a choice) or without (a line of text). It uses pi's own `select`/`input` dialogs. The daemon keeps the open request (`run.asking`), sends it to the chat as pi's `extension_ui_request`, writes the answer back, and ends it with `ask_end` (also on settle, exit, abort). A new viewer gets it in `history.asking`. Other dialogs pi may ask (`confirm`, `editor`) are cancelled at once. The question and the answer stay in the chat from the tool call and its result. |
| Agents' requests | An agent cannot change agents on its own (the profiles are root's, and its key may not call `/api/agents`), but it can ask: the `manage_agents` tool (`weilo.mjs`, `agents/manage.mjs`) lists the agents, the skills, the plugins and the extensions, and asks to make an agent or change one (itself too: name, instructions, model, thinking, skills, plugins, extensions; `extensions` names every one the agent should have, bundled ones too). The daemon checks the request as saving would, then asks the user itself in the asking agent's chat (`askUser` in `runner.mjs`: a `select` request of its own, `run.asking` with a `resolve`), with the whole change (`askUser` refuses one over 20000 characters, for `manage_settings` too, never cuts it) and what the agent would get that the asking one has not (another provider, plugins, extensions) or the browser. No request sets `isolated` or `trusted`, and an agent made by request is regular. An isolated agent lists only itself and what it could ask for, and asks only for its own skills, plugins and extensions; a regular agent cannot change an isolated one. A trusted agent (`trusted: true`, Edit agent > Access > Always allow its own changes) has a change to itself of only its instructions, thinking or skills applied without a question; the chat shows a line for it (the tool result's `details.note`). Nothing else is ever allowed always. Only a paired device answers it (`POST …/answer` is not an agent's route), so an agent cannot approve its own request, and it cannot skip the question by calling the route itself: the question is the daemon's, not its pi's. Unanswered (skipped, aborted, pi closed, another question) is no. A changed agent starts its pi anew (the asking agent's own once its reply ends). Changes to an agent run one at a time (`updateAgent` in `agents.mjs` queues them per agent) and apply to the profile as saved then; a change the user approved is refused (409, "was changed while the user was asked") if a field it sets changed while the user was asked, and the `skill` tool adds its skill to the agent's current list. The tools call the daemon with `node:http`, which waits as long as the user takes (`fetch` gives up after five minutes). |
| About you | `agent/USER.md` ("Name: …", then free text; editable by hand) holds what you tell the agents about yourself. The first screen asks for it (Skip is allowed), and Settings > About you changes it. Pi adds the file to every agent's system prompt (`--append-system-prompt`, only when the file exists), and saving restarts the agents. `GET`/`PUT /api/user`. |
| Memory | Two layers, shared by all regular agents (`daemon/memory/`; an isolated agent has neither and keeps notes as files in its folder, but its chat is searched and curated like the others'). **Hot memory** is `agent/MEMORY.md`: short facts about you, one per line (`- [m7 2026-10 preference] text`: an id, the month it was saved or last confirmed, and a kind: preference, fact, goal, person, project or decision; at most 40 notes or 3500 characters, 200 each). The file groups the notes under a heading per kind (Preferences, Facts, Goals, People, Projects, Decisions); notes not confirmed for 12 months go under "Not confirmed for 12 months: may be out of date". Changing a note confirms it (its month is now). Pi adds it to every agent's system prompt when it starts, so a change shows in the next start (turning Settings > Memory > Notes about you on or off restarts agents; `/reload` restarts one). The app does not show the notes; an agent changes or forgets one when asked. Agents write it with the `memory` tool (`remember` with `text` and `kind`, `forget`, `list`; the daemon refuses secrets, text that reads as an instruction or hides characters (`unsafe` in `common.mjs`, as Hermes checks its memory), near-duplicates and a full file, whose error lists the 5 oldest notes). A page may start with `sources: [<agent id>@<date>, …]`, the chats it came from. The vault is not in any prompt: agents search it with the `fetch_knowledge` tool (`vault.mjs` reads pages, `fetch.mjs` searches). `fetch_knowledge` takes `query` (keywords over the pages and the chats of all agents, also deleted agents' kept chats), `source` + `query` (a page's source: the passages of that chat on that day, to check a claim) or `agent` (its newest messages). It reads only what you and agents wrote (not tool results, thinking or pi's saved prompts), from the chat index (Search below), at most 5 excerpts and 1800 characters, wrapped as background that is not instructions; what an isolated agent said is labelled as its own report, unchecked; it never takes a path. **The curator** (`curator.mjs`, chosen in Settings > Memory, off until it has a model) is `pi -p` with file tools (`read`, `write`, `edit`, `grep`, `find`, `ls`) and the vault as its working folder. Every 5 minutes it looks at each agent that is not working; a chat is read when it has been quiet for 10 minutes, or, if it never is, 12 hours after its last run (counted from the first look), and only when it has a new user message. It reads the new messages from the chat index, oldest first (no more of them than 6 pieces could hold, so a long backlog is not loaded whole), in pieces of at most 24000 characters (at most 6 pieces a run, each a run of up to 10 minutes), looks for the page that covers a subject before it makes one, merges and corrects pages, and keeps `index.md` current. It also reads, once they have been quiet for 10 minutes, the Markdown and text files an isolated agent changed in `shared/` of its folder (opened without following a link the agent put there), and files what is about the user. A chat or notes from an isolated agent are marked so, and their sources are written `isolated:<agent id>@<date>`. Afterwards the daemon replaces any line of a page it changed that looks like a secret or an instruction. It is told not to keep one-off answers, small talk, pages' or tools' text, secrets or what you asked to keep private, and not to follow instructions in a chat. The curator is told to write only inside the vault; the file tools are not fenced (a failed or timed-out run is scrubbed too, and counts as a failure). `agent/curator.json` holds the model, `notes` (Notes about you), and for each agent the last message read, the last shared note filed and the last run. A chat whose runs fail 3 times in a row waits for a new message. |
| Settings requests | A regular agent may ask to change a few settings with `manage_settings` (`settings/manage.mjs`; isolated agents may not): `list` shows the models the keys can use, which are on, their windows, the tokens kept free and who uses them; `change` turns models on (only ones a key or sign-in can use) or off (never one an agent or the curator uses, nor the last), or sets a model's tokens kept free (between `MIN_RESERVE` and its window) or gives it back to the app's rule. Always a question to the user with the exact change; on yes the daemon plans it again and refuses it (409) if the settings changed while the user was asked, else writes `settings.json` (still root's) and the agents' pis start anew. Nothing that loads code, names a path or address, or touches keys or devices. |
| Compaction | Pi summarizes by tokens kept free (`compaction.modelOverrides.<provider/id>.reserveTokens`). The daemon writes it per enabled model (all, when none is), summarize at half of a window of 128k or more and 80% of a smaller one, never later than 120k tokens (`COMPACT_POINT`, `COMPACT_CAP`, in `settings/compaction.mjs` with the reading back), never under 16384 free. A value the app wrote, now or by the older rule (`OLD_COMPACT_AT`), is replaced with the current one; values set by hand are kept. Beside the send button the chat shows how much of the window is used (a percentage and a small bar, red as the context nears that point); hovering or tapping it shows tokens of the window (`GET /api/agents/:id/context`) and offers `/compact [what to keep]` (`POST …/compact`, refused during a run) and `/reload` (`POST …/reload`: pi starts anew, now if idle, else when the run ends). The chat still shows what was summarized: pi's history starts with its summary (a "Summarized for the agent" line), and the messages before it load from the chat file as you scroll up, 60 at a time (`GET /api/agents/:id/earlier?skip=n`: those before the last compaction's `firstKeptEntryId`, without thinking or tools' results other than `ask`, `action` and the older `routine` tool's). The parsed earlier messages are kept for the last 4 agents (`EARLIER_KEPT`), keyed by each chat file's size and time, so later pages are slices of what was read, not a new read of the files; only what the chat shows is kept. A search result older than what is loaded loads pages until it is there. **Earlier and smaller:** an agent that settled is summarized after 5 seconds (`IDLE_COMPACT_DELAY_MS`) if its context is at 75% of the point or more (`IDLE_COMPACT_AT`, `compactIdle` in `runner.mjs`); a message or `/compact` meanwhile waits for it, and the pi is not closed while it runs. `weilo.mjs` (with `context.mjs`) changes what pi sends: on pi's `context` event, tools' results from before the user's second-to-last message longer than 2000 characters are cut to their first 400 with a note, and their images left out; the cut moves only when the user writes, so the start of what is sent stays the same between two user messages and the provider's prompt cache holds. On `session_before_compact` it sends the messages to summarize as text (each tool's result cut to 1500 characters, the whole to 120000, start and end kept) to `POST /api/agents/:id/summary` (`agents/summary.mjs`), which runs `pi -p` without tools on the curator's model, as the curator's user, with a key of its own beside the curator's (`extraKey`), and an assistant's summary format (what the user wants, about the user, done, open, decisions, next steps, details to keep), adding for agents that have `fetch_knowledge` that older messages can be found with it. Without a curator model, or when that fails, pi writes its own summary. |
| Actions | One-tap versions of what you ask an agent often, proposed by the agent and approved by you: a saved request with blanks (agent), or a script it wrote that runs without the model (script). See Actions under Daemon. |
| Actions | Things an agent does for the user: with a tap, and, if they choose, by themselves at set times (once, every few minutes, hourly, daily, weekdays, weekly). The agent proposes them and the user approves them. Kept in `agent/actions.json`. See Actions under Daemon. |
| Browser | One Chromium on a virtual screen inside the container; each agent has its own window with its own tabs, all sharing one set of logins. You watch it in the chat's side panel and can take over. Agents are asked to check with you before anything that cannot be undone (a request, not a lock). See Browser under Daemon. |
| Notifications | Web Push, without a library (`daemon/push.mjs`): the daemon makes its own VAPID key pair (`agent/push.json`, with the browsers that turned notifications on and the agents muted), encrypts each notification for one browser (RFC 8291, aes128gcm) and posts it to that browser's push service (only Google's, Apple's, Mozilla's or Microsoft's addresses are accepted). The runner sends one when a run ends (the answer's start, or its error; a run you stopped sends none) and when the agent asks you something. None while the app is on screen anywhere: the agent list asks `GET /api/agents?seen` every few seconds while visible, and 15 seconds after the last, notifications go out again. The service worker (`ui/public/sw.js`) shows them, one per agent, and a tap opens the app at that agent (`?agent=`, or a message to an open window). On iPhone, only from the app added to the Home Screen. |
| Search | `GET /api/search?q=` asks the chat index (`agents/chats.mjs`): SQLite (`node:sqlite`, built into Node) with an FTS5 trigram index of what you and the agents said in every chat, deleted agents' kept chats too. Chat files only grow, so each search first reads only what was added since (a file that shrank or went is read again or dropped); the index is built at start too, so the first search is fast. It is the app's own: `agent/index/chats.db` (the folder 0700, root's), kept in the data folder, so an image update does not lose it (it was `/var/lib/weilo/chats.db` in the container, made again after every restart). The find bar searches the chat on screen and marks matches with CSS highlights (`::highlight(find)`), so the messages' markup is untouched. |
| Agents' questions | A regular agent can ask another agent something with `ask_agent` (`agents/manage.mjs`): the user approves the exact message in the asking agent's chat, the other agent answers it in its own chat (refused while it is working), and the answer comes back wrapped as that agent's report (`<reply from=… isolated=…>`), not instructions. | Budgets | An agent may have a daily token limit (`dailyTokens` in its profile; Edit agent > More options > Model settings). Three Docker volumes sit beside it: `tools` (`~/.local`: what agents install with npm and pip), `browser` (Chromium's profile: logins and cookies) and `sandbox` (the sockets between the app and the sandbox).

Repo: `compose.yaml`, `image/Dockerfile` and `image/pi/` (pi's pinned packages), `daemon/`, `ui/`, `package.json` (the daemon's check). The daemon runs in the container as
its main process on port 3210 (published on `127.0.0.1` only) and serves the built UI.

## Architecture

```
browser ─► 127.0.0.1:PORT ─► weilo-core container
                              └─ daemon (Node, no dependencies)
                                  ├─ api.sock ◄──────────── weilo-sandbox container (own network, no keys)
                                  │                          └─ sandbox/server.mjs ─ ctl.sock: start a program
                                  │                              └─ per isolated agent / its plugin: own pid, mount,
                                  │                                 ipc, uts namespaces; only its own folder
                                  ├─ static UI
                                  ├─ JSON API + SSE
                                  ├─ one `pi --mode rpc` per open agent
                                  └─ Xvnc + openbox + Chromium (the browser)
```

The host launcher is `docker compose up -d` (both containers) plus opening the browser.

## Daemon

**Job:** serve the UI, manage agent files, write provider keys, run pi, relay its events.

**Open an agent** (as its own user, with its own `PI_CODING_AGENT_DIR` (Keys above) and `HOME` (`homes/<folder>/`, `isolated-homes/<folder>/`); cwd its home; the session is found by `--session-dir` and `--session-id`, not by the folder). A regular agent:
```
/usr/local/bin/pi --mode rpc [--model <m>] [--thinking <level>] \
   --append-system-prompt agent/profiles/<id>/agent.json --append-system-prompt <folder rules> \
   [--append-system-prompt agent/USER.md] [--append-system-prompt agent/MEMORY.md] \
   -ne -e builtin:mcp -e builtin:codemode -e builtin:tool-search -e builtin:llama.cpp \
   -e /app/weilo.mjs -e /app/memory/extension.mjs [-e /app/<feature>/extension/<entry> …] [-e agent/extensions/<name>/<entry> …] \
   --no-skills [--skill agent/skills/<skill> …] \
   --tools read,bash,edit,write,show,ask,manage_agents,skill,memory,fetch_knowledge,manage_settings,ask_agent[,browser][,action][,<extension tools> …][,codemode,mcp__<plugin>__* …]   (--no-mcp when it has no plugin) \
   --session-dir agent/sessions/<id> --session-id <id>
```
An isolated agent, in the sandbox (cwd `isolated/<folder>/`; `<pi dir>` is its `PI_CODING_AGENT_DIR`, written by the sandbox; its skills and added extensions are mounted read only, at the same paths):
```
/usr/local/bin/pi --mode rpc [--model <m>] [--thinking <level>] \
   --append-system-prompt <pi dir>/agent.json --append-system-prompt <isolated rules> --no-context-files \
   -ne -e builtin:… -e /app/weilo.mjs [-e /app/browser/extension/index.js] [-e /app/actions/extension/index.js] [-e agent/extensions/<name>/<entry> …] \
   --no-skills [--skill agent/skills/<skill> …] \
   --tools read,bash,edit,write,show,ask,manage_agents[,browser][,action][,<extension tools> …][,codemode,mcp__<plugin>__* …] \
   --session-dir isolated-sessions/<id> --session-id <id>
```
The session id is the agent id, so opening an agent always resumes its one conversation
(pi compacts long history itself). Pi has no profiles; this command is the profile. Checked on pi 1.1.0: a model that does not exist exits with
an error; a missing instructions file does not (pi starts without it).
An agent's pi loads only pi's built-in extensions (`PI_BUILTINS` in `config.mjs`) ours, and its extensions (above): `-ne` turns off discovery, so an extension left in `agent/extensions/` or named in `settings.json` never runs in an agent. `-ne` also drops the built-ins, so each is named again; one left out is lost (`mcp` is plugins, `codemode` and `tool-search` come with them, `llama.cpp` is the `/llama` provider). Checked on pi 1.1.0 with a probe extension and an MCP plugin: the tools and commands match the old command line. A project's `.pi/extensions/` was already not loaded (pi's project trust).

**Actions:** things an agent does for the user, with a tap and, if they choose, by themselves at set times (`actions/actions.mjs`, kept in `agent/actions.json` with the user's time zone). Older versions kept timed tasks in `agent/routines.json`: on first use each becomes an agent action with that schedule (its next time and last error kept) and the file is removed. The agent proposes an action with the `action` tool (`actions/extension/`, ops `list`, `try`, `create`, `update`, `delete`, `run`); `create` and `update` wait for the user's approval in the chat (`askUser`), in plain words ("Ada would like to add a button: …", with what it runs below), with the choices "Add the button" (or, with a schedule, "Add it, and run it every day at 08:00", "Add the button only") and "No thanks". `delete`, and an `update` that only sets `schedule` to null, need no approval: they only do less. The user can also make one (the + in the panel: a name and what the agent should do, an agent action, `POST /api/agents/:id/actions`) and rename it or change what it asks for (Edit on its screen); an Instant one's code changes only through the agent. An action has a title, a line `about`, an icon, `fields` (`{name, label, options?, default?}`, at most 8), a kind, an optional `schedule` and its last 20 `runs` (`{at, ok, text, by: "you" | "schedule", ms?, chat?}`). An **agent** action is a `request` with `{name}` blanks: it goes to the chat as a message that starts with `⚡ Action: <title>` (`steer` if a run is active), plus a line telling the agent to confirm with `ask` before it pays, orders, books or sends, tapped or run by itself (the tool tells it never to make a script that does); the chat shows it as your message with the action's name above it and that line hidden. Run by its schedule, the first line ends with ` · ran by itself` and a line tells the agent the user is away (do it now; confirm with `ask`, which notifies them; leave anything else that needs them for the end); the chat shows it as a line "<title> ran by itself" (older timed tasks, `⏰ Routine: …`, show the same way). A **script** action (shown as Instant) is an ES module (`export default async function ({ input, browser })`, at most 16,000 characters) the daemon runs without the model (`runScript`): `actions/run.mjs` runs as the agent's user, in its folder, gets the script and the field values on stdin, imports the script from a `data:` URL (so only `node:` modules can be imported), and writes the answer as the last line of stdout; it is stopped after 90 seconds. `browser(args)` posts to the agent's browser route with a key of its own (`scriptKey`), which the route loop lets through to the `browser` route only (not the model proxy, nor any other tool) and which is dropped when the script ends. The script itself is kept in `actions.json`, not in the agent's folder, so the code that runs is the code the user approved. Its answer (a string, or an object shown as one "name: value" line each) is kept in `runs`; it may return `stop: true` (the order arrived), which ends its schedule. **Schedules** (`actions/schedule.mjs` has the time math): `every` is once, minutes (`minutes` 5, 10, 15 or 30), hour, day, weekday or week; `times` are one or more "HH:MM" (hour and once take one); `date` is for once (`YYYY-MM-DD`, `today`, `tomorrow`, or `in_minutes`). Times are wall-clock times in the user's time zone: the browser's (it sends `X-Timezone` with every request; listing the actions on a paired device keeps it, and when it changes the recurring schedules on the old zone move to the new one). A time that a clock change repeats runs once, at the earlier time; one it skips runs at the later time. Every 30 seconds the daemon runs what is due as if tapped, with the fields' defaults (an action that runs by itself needs one for each field); its next time is saved first, so a crash skips a run and never repeats one; one missed by more than an hour (the computer was off) is noted "Missed: …" and waits for its next time; a once schedule ends after it runs. Older versions had "Ask me first" (`confirm`) and runs waiting for the user (`waiting`): both are ignored now. A script's answer by itself is also a notification. An open chat hears `actions_changed` on its event stream and reads the actions again. In the app, the bolt in the chat's top bar opens the Actions & pins panel, with a tab for each (the globe opens the Browser; one at a time, on a narrow screen as a sheet): each action with ▶ to run it now, Instant for a script, its last answer, and when it runs by itself ("Every 10 minutes · next in 8 min"). Tapping one opens its screen: Its request (three lines, with Show more), Run now, Schedule (Once, Every few minutes, Every hour, Every day, Weekdays, Every week; the time, day or date; its next time), its recent runs, and Delete; changes save as they are made (`PUT …/actions/:rid`, the user's, no approval). Scripts' answers are kept in the chat by their time, as cards the agent does not see ("you tapped it" or "ran by itself"; Run again and Ask the agent about it; when one did not work, Ask the agent to fix it, which sends the error so it fixes the script with `try` and `update`). An action with fields opens a small form, filled with the values used last (kept in the browser).

**Pins:** small cards an agent keeps up to date for the user, on the Pins tab of the bolt's panel (`actions/pins.mjs`, kept in `agent/pins.json`; the `pin` tool comes with the actions extension). A pin is a `status` (a `value` like "$199", one `detail` line with an optional `tone` of good or bad, a `source`, optional `steps` like 3 of 4) or a `list` (`items`, each `{text, done}`, at most 30); at most 12 an agent. The agent pins when the user asks it to keep an eye on something or keep a list (ops `list`, `pin`, `update`, `unpin`); pins only show things, so they need no approval, and the chat shows "Pinned: <title>" (a button that opens the Pins tab and outlines that pin for a moment) or "Unpinned: <title>". A number in a value is kept in `history` (the last 30) for a small chart. A pin can name the `action` that keeps it fresh: a script returns `{ pin: {…} }` and its pins take it (the run then reads as the pin's line, "AirPods Pro: $189"); an agent action's message ends with a hidden line telling the agent to update its pins. When such a script runs by itself, it notifies only when a pin changed (or it failed). Deleting the action leaves its pins, unlinked. The user ticks list items and removes pins in the app; the agent sees ticks in `list`. `changedAt` (what the pin shows changed) drives a dot on the bolt and the Pins tab until the user looks (the time they last looked is kept in the browser); the panel opens on Pins when there are any. The chat hears `pins_changed` on its event stream.

**Browser:** one Chromium and a virtual screen in the container. `browser/screen.mjs` starts them on first use (`wakeScreen`, waiting up to 20 seconds: an agent's first browser step or a take over; not at the daemon's start, so it uses no memory until it is needed; until then the live view shows nothing) and starts them again if they stop: Xvnc (1280x800, on a unix socket only), openbox (no window frames, windows maximized; a pop-up such as a Sign in with Google window, and a dialog, keep a frame with a close button), and Chromium (profile in the `browser` volume, so logins stay), all as the user `node`. Nothing else in the container reaches them: the VNC socket and the display's Xauthority cookie are in `/tmp/weilo-screen/` (`node`'s alone), Xvnc takes X clients with that cookie only (so an agent cannot type into the browser), and Chromium has no debugging port: it runs with `--remote-debugging-pipe`, and the daemon passes that pipe (NUL-ended JSON) to a WebSocket at `/api/browser-cdp/<secret>` (a secret made at each start) for its own Playwright. The live view is a WebSocket at `/api/browser/view`, for paired devices: the daemon turns it into plain VNC on the socket. Pages cannot reach the app (port 3210): a Chromium policy (`image/chromium-policy.json`) blocks it, and the `browser` tool refuses it with a message. `browser/browser.mjs` drives Chromium with `playwright-core` (installed from `image/pi/` in the image and found through `NODE_PATH`; the daemon has no npm packages). All agents share the browser and its logins, and **each agent has its own window with as many tabs as it needs**: the browser's window id tells them apart, so a tab that a page opens joins its agent's window, and an agent only sees and uses the tabs of its own window. An agent reads a page as text (Playwright's accessibility snapshot, where each element has a ref such as `e13`) and acts with `click`, `type`, `press`, `scroll`, `back`, `open` and tab actions; each step returns the page again. An agent's steps run one after another. Background tabs are not slowed down (agents work in them), so an agent's window is closed when it has not used it for 10 minutes and is not working (not while you watch the screen or have taken it over), and the screen, the window manager and Chromium stop after 20 minutes with no step, no take over and no live view (`sleepScreen`); the next step or take over starts them again, with the same sign-ins. A window that you closed opens again at the agent's next step, and one that you minimized comes back (the screen has no taskbar). Deleting an agent removes its profile and actions first (so nothing starts its pi again), then stops it, waits for a running browser step, closes its window and removes its chat. The `browser` tool (`browser/extension/`) calls `POST /api/agents/:id/browser`.

**Take over:** the panel at the top of the chat's right-hand side shows the screen with the agent's window in front. Take over stops the agent's run (`abort`), waits for a step that was running, opens its window if there is none, and lets you use it; the agent's browser steps are refused until you give it back. Give back sends the agent a message to read the page again and carry on (only if its run was stopped). The agent list shows "You have the browser" for an agent you took over, also when you open another chat. A window that another agent opens does not cover the one you took over.

**The browser:** an agent that has the browser tool can do what it likes in the browser, whose sign-ins every agent with the tool shares; it does not ask first. Keys, the paired devices and other agents' chats are kept from agents by their users and by the key gateway (Users and Keys above).

**Events:** relay pi's own events unchanged (`message_update` text/thinking/tool-call
deltas, `tool_execution_*`, `agent_settled`). They already are a typed streaming protocol,
so there is no AG-UI translation layer; the UI renders pi's events. (AG-UI stays an option
if other frontends appear.)

**Stream:** SSE, one JSON event per message. First `{type:"history", messages, busy}`, then pi's
events, and `{type:"exit", code, error}` when pi ends (`error` is pi's last stderr line, e.g.
"Model … not found"; exit code 0 is a normal restart).

**Process rules:** one pi per open agent, started on first use (the daemon loads pi's model runtime at its start, `warmModels`, so the first one starts faster). It stops after 10 idle
minutes with no viewer and no run (`IDLE_MS`), or after 90 seconds (`GLANCE_MS`) if it was opened but never given a message (a chat you only looked at), on delete, on shutdown, and when its agent, a skill or a
plugin changes (so the change applies: at once if idle, else when the run ends; viewers
reconnect to the new pi). A message during a run is queued into it (`steer`). Split RPC lines
on LF only (not Node `readline`). pi's RPC lines, websocket frames and the browser's CDP pipe are put together from a
list of chunks (`splitOn` in `common.mjs`; `readMessages` in `http/websocket.mjs`), not by adding each chunk to a string
(a 16 MB line took 2.2 s, now 31 ms; a 32 MB frame 9.5 s, now 67 ms). A connection dropped during a websocket or
plugin-pipe upgrade, or on the admin socket, is closed (an error handler is set first), never a crash.

**Shutdown:** on SIGTERM or SIGINT the daemon closes its two servers, stops every pi (`SIGTERM`, then `SIGKILL` 5 seconds later if it hangs; `PI_KILL_MS`), waits for queued JSON and audit writes, and exits, within 12 seconds at most (`SHUTDOWN_MS`; compose gives it 15, `stop_grace_period`).
**Watchdog:** a worker thread (`watchdog.mjs`) watches a counter the main thread bumps every second; if the event loop is stuck for 120 seconds (`HUNG_MS`) it logs that and kills the daemon, and Docker starts it again (`restart: unless-stopped`).
**State files:** `writePrivate` (`common.mjs`) writes to a temp file of its own (`<file>.<pid>-<n>.tmp`, 0600), `fsync`s it and renames it in place, so a crash or power cut leaves either the old file or the new one. `updateJson` first keeps the previous good version as `<file>.bak` (0600, root; not for `devices.json`, so a removed device never comes back). `readJson` reads a file that is not valid JSON from its `.bak`, keeps the broken one as `<file>.corrupt` (a hand edit is not lost) with a line in the log, and fails only when the `.bak` is bad too.

**Access:** the port is published on `127.0.0.1` only, and the daemon rejects
requests with an unexpected `Host` or `Origin`, and anything another site loads from it
(`Sec-Fetch-Site`; a plain link still opens the app). This blocks other websites and DNS rebinding.
Being on this computer is not enough, though: an agent in the container reaches the published port too (Docker passes
`host.docker.internal:3210` on to it), with any `Host` it likes. So the daemon knows who calls (`http/access.mjs`):
- **Paired devices.** A browser pairs once with an 8-character code (40 bits; 10 minutes; one use; 10 wrong codes in 10
  minutes stop pairing for 10 minutes) and gets a random key as an `HttpOnly`, `SameSite=Strict` cookie (`Secure` on a
  `.ts.net` host), kept for 400 days. `agent/devices.json` holds each device's name, dates and the key's SHA-256, never
  the key. Codes live in the daemon's memory. A paired device makes one in Settings > Devices; the first one comes from
  `pair.mjs` (`docker exec weilo-core node /app/pair.mjs`), which asks the daemon over a unix socket in a folder only the
  daemon's user can open (`/tmp/weilo-admin/`) and prints a `/?pair=<code>` link. The start scripts open that link.
  `POST /api/pair` `{code}` is the only API call without a cookie (its body is read up to 1 KB, `MAX_PAIR_BODY`); any other gets 401 `{pair: true}`, and the UI shows
  its pairing screen. The static UI itself is public. `http/static.mjs` serves it compressed (brotli or gzip, as the browser
  accepts, made once per file and kept in memory) with an `ETag` (304 when unchanged), `Referrer-Policy: no-referrer`,
  `X-Content-Type-Options: nosniff` and `Content-Security-Policy: frame-src about:; frame-ancestors 'none'`; a missing `/assets/` file is a 404,
  not `index.html`. JSON replies carry `X-Content-Type-Options: nosniff` too.
- **Agents.** Each pi gets a random key when it starts (`WEILO_KEY`, dropped when it stops); its tools send it as
  `Authorization: Bearer` (`tool.mjs`). With it a pi may only call the routes of its own tools (`agentRoute` in
  `server.mjs`: browser, skill, manage_agents, manage_settings, ask_agent, memory, fetch_knowledge, action), for
  itself; anything else is 403. An isolated agent is also refused what `mayCall` (`agents.mjs`) refuses it, and its key works
  only on the sandbox's socket (`checkPlace` in `server.mjs`), where nothing else works.

**Remote use:** the host may also be a Tailscale name (`*.ts.net`), and an `https://` origin of the same host is accepted. On the host, `tailscale serve --bg 3210` forwards the tailnet's HTTPS address to the published port, so the port itself stays on `127.0.0.1`. A phone on the tailnet still has to be paired.

**Files** (`daemon/`, copied to `/app` in the image; Node built-ins only, plain relative imports):

```
server.mjs          entry: the API's routes, the two servers (the app's port, the sandbox's socket), the background jobs, shutdown
watchdog.mjs        kills the daemon when its event loop is stuck for 120 s, so Docker restarts it
config.mjs          the values to tune (port, timeouts, limits, intervals), grouped by feature
common.mjs          data paths, errors, private JSON and text files (flushed, with a last good copy), openChat, splitOn (lines and frames from chunks)
weilo.mjs           the pi extension (`-e /app/weilo.mjs`): show, ask, skill, manage_agents, manage_settings
tool.mjs            what the bundled extensions share: the API call and the tool helper
version.mjs         what this build is (version, commit, pi), from the image's environment and pi's package
audit.mjs           the audit log (agent/audit.jsonl)
migrate.mjs         brings the data folder to this app's data version at start (weilo.json)
pair.mjs            prints a link that pairs a browser (asks the daemon over its admin socket)
users.mjs           who runs what (the Linux users, the PATH they get), and who may read what (owners and modes, set at start)
gateway/            models.mjs (the models' keys and sign-ins: the proxy, the placeholders), plugins.mjs (the plugins' secrets: the proxy,
                    the pipe, where a plugin runs), forward.mjs (the streaming they share), pipe.mjs (run by an agent's pi)
sandbox/            server.mjs (the sandbox container's program), enter.mjs (sets up a program's namespaces), spec.mjs (what it
                    may be asked to start), frames.mjs (its output to the app), client.mjs (the app's side)
http/               request.mjs (Host/Origin checks, JSON body and reply), access.mjs (paired devices, agents' keys), static.mjs (the UI, compressed, ETags), websocket.mjs,
                    events.mjs (SSE), files.mjs (the files agents' chats name)
agents/             agents.mjs (profiles; every path of an agent, and what an isolated one may call), runner.mjs (pi processes), manage.mjs (agents' requests, ask_agent), pidir.mjs (what a pi is given), pi.mjs (RPC framing),
                    sessions.mjs (chat files: earlier messages, kept for the last 4 agents; newest message for the list), chats.mjs (the chat index), usage.mjs (tokens and cost per day), uploads.mjs (attachments)
memory/             memory.mjs (the MEMORY.md notes), vault.mjs (the vault's pages), fetch.mjs (search), curator.mjs (the curator)

                    rule.mjs (ask first)
settings/           providers.mjs (keys, models), compaction.mjs (when pi summarizes), manage.mjs (agents' settings requests), plugins.mjs, skills.mjs, extensions.mjs, zip.mjs (the unzip checks they share), user.mjs (About you)
```

Each of `browser/` and `actions/` has an `extension/` folder (`weilo.json`, `index.js`): the bundled extension that gives agents its tool (memory's is `memory/extension.mjs`, loaded for every regular agent). They run inside pi,
not the daemon, and only call the daemon's HTTP API (`tool.mjs` has the shared call); it may import plain constants (`config.mjs`, `actions/schedule.mjs`), so the limits and
schedule words in its tool descriptions are the daemon's own.

The UI repeats a few of `config.mjs`'s limits in `ui/src/lib/limits.ts`. Keys are not verified
when saved: a bad key shows up as pi's provider error in the conversation.

## Frontend

React 19, Vite, Tailwind 4, TypeScript; `react-markdown` + `remark-gfm`, `lucide-react` (icons)
Geist (two fonts) and noVNC (the browser's screen, loaded on first use) are the only other dependencies. The look (tokens, UI kit in
`components/ui`, avatars, bubbles) is ported from the earlier weilo-agents app; the brand (logo,
favicon, Lucide icons, Geist, the Weilo Theme's ember colours) is weilo-brainweave's. The data
layer is ours. Built in a Docker build stage, so the image holds static files only. No router or
data library. Dark and light by system setting; Settings > General picks Light, Dark, or the
Weilo Theme (`data-theme` on `<html>`, which overrides the colour tokens).

- Sidebar: the name "Weilo Agents" as plain text, a search of all chats, then agents (avatar, name, newest message as plain text; an unread one has its time in the unread colour and a dot at the end), + New agent, Skills and Plugins (on a phone; a computer shows them in Settings beside its pages), Settings. Drag an agent to reorder (hold first on a phone). On a
  phone, list and chat are separate screens; the chat (or Settings) is a step in the browser's history, so the phone's back button or gesture returns to the list, and from the Home Screen on an iPhone a swipe from the left edge does. Edit agent opens from the chat's title, and Delete (with its choice to keep the chat) is in that form; it has
  avatar, name, instructions, then cards of rows: Model (provider, model, thinking), Built-in extensions (a switch each) and Add-ons (skills, plugins, extensions: each row says what is on and opens a list of switches, or "Add" when there are none).
- Chat state is one reducer over pi's events (`features/chat/useChat.ts`): history, then live
  text, thinking and tool-call deltas. `conversation.ts` holds the reducer and maps pi's messages to bubbles.
  Thinking is not shown. What the agent did between its words (its tools, and what it said while using them) is one folded line ("Read 2 files · Ran a command") that opens to each step; `show`, a question the agent asks and a line for what it did with an action show as themselves. An agent's text appears when its message is complete, so text that comes with a tool call never flashes; a pill above the composer says "Working" (or "Waiting for your answer") with a Stop button. The composer floats over the chat. While the agent waits for your answer, a message you type in the box is the answer, and number keys pick its options. While it works, a message goes in with `when: "now"` (pi steers: it reads it before its next step) or `"later"` (a pi follow-up, after it finishes); `unqueue` takes a queued one back (pi clears its queue only as a whole, so the daemon queues the rest again, with their images). An empty chat shows starters; the draft is kept per agent in `localStorage`.
- Composer: text, attachments (files and photos, camera, paste, drop) and voice typing; typing "- " or "1. " starts a list that a new line carries on. The + offers Files and photos, Camera, and Skills and commands (what typing "/" offers). Disabled
  with "Add a provider" until a key exists. Stop appears while a run is going. A failed start
  closes the stream and shows pi's message with Try again; a clean restart reconnects by itself.
- Settings, Skills and Plugins are one page in place of the chat (`features/settings/SettingsView.tsx`; the chat stays mounted behind it, so a draft survives; opening it reads the lists again): a menu on the left in four groups (You: About you, Memory; Models: Providers, Usage; What agents can use: Skills, Plugins, Extensions; App: Devices, which is the paired devices and the activity on one page, and General, which is appearance, notifications and About on one page; it opens at About you; on a phone, the list of pages first, each with what it holds at a glance ("1 connected", "2 skills"), then the page with a back arrow) and a page on the right made of rows (`components/ui/Row.tsx`: title and description on the left, the control on the right). The sidebar's Skills, Plugins and Settings buttons open it at their page.
- Settings > Usage (`features/settings/UsagePage.tsx`, `api/usage.ts`): tiles for today, the last 14 days and the estimated cost; a bar per day of tokens, stacked by agent (8 colours, the rest as Other); and a row per agent with today's tokens, its daily limit, 14 days' tokens and cost.
- Settings > Providers: a key field per provider, Connected tag, Models (which ones agents can
  pick), Remove. Keys go to the daemon only.
- Model is two dropdowns: a provider, then one of its enabled models (all of them when none is).
- Speed: chat text is memoized (`Markdown`, `AgentText`, `CardText`), so a message's Markdown is parsed once, not on every
  streamed delta (a 200-exchange chat at 4x CPU: the longest freeze while streaming went from 2.3 s to 0.13 s, idle script time
  from 4.8 s to about 0 per 10 s). The agent list is set again only when it changed, and reloads that come together run as one.
  The browser and actions panels do not poll while the tab is hidden. Settings and the agent form load on first open (`lazy` in
  `Workspace.tsx`; the main bundle went from 533 KB to 456 KB, gzip 161 KB to 141 KB).
- Dev: `npm run dev` in `ui/` (proxies `/api` to the container).
