Development

How the repository is laid out, the conventions it follows, how to run it while you work, how to extend it without opening a hole, and the invariants that hold the security model together.

Conventions

  • No comments in code. The code is kept short and named plainly; the reasons behind it live in these pages and in DESIGN.md. A change that alters behavior, a boundary or a limit updates the page that describes it in the same commit. If a page and the code disagree, the code is right and the page is the bug.
  • Checks. npm run check type-checks the daemon (TypeScript on its JavaScript, with unused locals as errors) and npm test runs its tests (daemon/test/, node:test, no other library); npm run build in ui/ type-checks and builds the UI. CI runs all three on every pull request, builds the image and checks that the sandbox makes namespaces. A change to a rule (who may call what, a check, a limit) comes with a test. What only a real install shows stays on the release checklist.
  • The daemon has no npm dependencies. Node built-ins only; the two packages it uses at run time (pi's SDK and playwright-core) are installed in the image from image/pi/package-lock.json and loaded by path or through NODE_PATH. The root package.json holds only the checks' tools.
  • One place for numbers. Limits and timeouts live in config.mjs. The UI repeats a few in ui/src/lib/limits.ts: change both together. Tool descriptions are built from the same constants.
  • Errors are fail(status, message); the message is shown to the user or the agent as is, in plain words. Unexpected errors are logged and answered as "An error occurred".
  • Files are written whole (writePrivate) and one change at a time (updateJson). A corrupt JSON file throws and is never overwritten.
  • Words: user-facing text is short, plain English; the UI says "agent", "folder", "add-on", never internal names.
  • Releases: VERSION and CHANGELOG.md change together; see RELEASING.md.

Running it while you work

docker compose up -d --build      # build and run both containers from this checkout
npm install && npm run check && npm test   # the daemon's type check and tests
cd ui && npm install
npm run dev                        # UI on http://localhost:5173, /api proxied to :3210
npm run build                      # type-check and build the UI
  • The dev UI talks to the container's daemon, so you need a running container and a paired browser. Cookies are not tied to a port, so a browser paired at localhost:3210 is paired at localhost:5173 too; otherwise open http://localhost:5173/?pair=<code> with a code from docker exec weilo-core node /app/pair.mjs.
  • After changing the daemon, rebuild: docker compose up -d --build. Logs: docker logs -f weilo-core.
  • The daemon's paths are fixed to the container (/home/node/.pi, /var/lib/weilo, /app). Running it directly on a host ("host mode") is not in this version. When it does not run as root it changes no owners and starts everything as itself, which is only good for experiments.
  • A build from a checkout is version dev: no update check.

Adding a route

Routes are registered in server.mjs. Pick the right kind first:

KindRegister withWho can call
For you (the app)route(method, path, handler)Paired devices only. An agent key gets 403.
For an agent's toolagentRoute(method, "/api/agents/:id/…", tool, handler)Devices, and the agent whose id is in the path, if mayCall(agent, tool) allows (an isolated agent only through the sandbox's socket).
  • A handler gets {id, rid, body, query, headers, who} and returns the reply object, or nothing for 204. A path under /api/agents/:id loads the agent first, so a missing id is 404.
  • Streams and file downloads are matched before the loop and check who.device themselves; do the same for anything that returns chat contents or files.
  • If pis read what the route changes when they start, wrap it in forAll so every pi starts anew.
  • A route that changes something is recorded in the audit log by the route loop; register it with quiet ({ audited: false }) only if it is a chat's own traffic.
  • Never return a secret: keys, plugin env or tokens, device keys.

Adding a tool

  1. Write the daemon side as a function in the feature's module, then an agentRoute named after the tool.
  2. Declare the tool in pi: in weilo.mjs with daemonTool(pi, name, label, description, parameters, required) for a chat tool, or in a feature's extension. The description is what the model reads: build any limit in it from config.mjs.
  3. Add the name to CORE_TOOLS in config.mjs if it is one of ours that every agent loads, so it reaches --tools and RESERVED_TOOLS. If it reaches anything all agents share (the library, memory, settings), add it to SHARED_TOOLS: mayCall then keeps it from isolated agents, both in --tools and on the route.
  4. If the tool changes something you should approve, ask with askUser(id, title, options) and act only on the exact approved option. Show the whole change; do not cut it.
  5. In the UI, give it a label in DOING (ui/src/api/agents.ts) and in StepsLine.tsx.
  6. Update the tools table and add a probe to the checklist.

Adding a bundled extension

  1. Make daemon/<feature>/extension/ with a weilo.json (apiVersion 1, name equal to the feature id, title, description, entry, tools) and an index.js that only calls the daemon's API through tool.mjs. It may import plain constants from the daemon, nothing that runs.
  2. Add the id to BUNDLED in common.mjs. It is then on for every agent unless its disabled list names it, and the Edit agent form shows a switch.
  3. Register its routes with agentRoute using the extension id as the tool name, so mayCall refuses an isolated agent that has it off.
  4. If it gives access beyond the agent's own folder (like the browser's shared logins), decide whether a new isolated agent should start with it off (withoutBrowser in agents.mjs) and whether more() in manage.mjs should warn about it.

An added (uploaded) extension needs no code change; its checks are in settings/extensions.mjs.

Adding a setting

  1. Keep it in a root-owned file in agent/ (0600, set by secure()), through readJson/updateJson, with a path constant in common.mjs.
  2. Add device routes (route) to read and change it; validate types and lengths, and put limits in config.mjs (and limits.ts if the UI enforces them).
  3. If pis need it at start, pass it in argv or env in runner.mjs and wrap the save in forAll.
  4. Add a page or a row to SettingsView.tsx (MENU and the page switch).
  5. Only if agents should ask for it, extend manage_settings: a field in FIELDS, its rules and its question lines in planSettings. Never anything that loads code, names a path or an address, or touches keys or devices.

Adding an agent field

  1. Validate it in clean() and give it a default in getAgent (agents/agents.mjs).
  2. Decide who may set it in agents/manage.mjs: requestable (FIELDS), for isolated agents too (ISOLATED_FIELDS), allowed always for trusted agents (TRUSTED_FIELDS, only if it gives no more reach), or the user's alone (USER_ONLY).
  3. Use it where the pi starts (argvOf, kindOf in runner.mjs), or wherever it acts.
  4. Add it to the Agent type in ui/src/api/agents.ts and to AgentForm.tsx.
  5. If old profiles need a value written, raise DATA_VERSION with a step in migrate.mjs.
  6. Update the profile table and the profile line in DESIGN.md.

Invariants that must not be broken

  1. The daemon is the only root process. Everything else is started with spawnAs (setpriv, no capabilities), except the model-listing pi, which runs in agent/ with every loader switched off.
  2. Root starts programs only by full path (BIN), with PATH = SYSTEM_PATH. Agents' tool folders come after root's folders, never before.
  3. No provider key, sign-in refresh token or plugin secret is ever written where a pi can read it. Pis get the gateway's address and a key of their own.
  4. An agent key reaches only agentRoute routes, for its own id, and only what mayCall allows. --tools is built from the same mayCall.
  5. Events, files, answers, agents, devices and settings routes are for paired devices only.
  6. Questions that approve something are the daemon's (askUser), show the whole change, are refused rather than cut over MAX_APPROVAL, and are answered only through the device route.
  7. isolated and trusted are set only by the user. Trusted applies only to the agent's own instructions, thinking and skills.
  8. Root sets owners only through folder() / newFile() (O_NOFOLLOW), keeps a pi folder its own until written, and never reads an agent's file through a link (the curator opens shared/ notes with O_NOFOLLOW and checks the real path).
  9. A uid is never given twice (newUid, lastUid).
  10. An isolated agent and its plugin programs run only in the sandbox; its key works only on the sandbox's socket, and only isolated agents' keys work there (checkPlace). The sandbox mounts nothing but the isolated agents' places and, read only, the skills and extensions; checkSpec refuses anything else, root, and links. A folder move runs with the pi stopped (holding).
  11. A plugin program never runs as an agent or in a folder an agent writes.
  12. What an isolated agent said or wrote reaches other agents only labelled as its report.
  13. The daemon runs with umask 007: nothing it makes is readable by everyone.
  14. Ids and folder names match ^[a-z0-9-]+$ before they become paths. Generated agent ids always end in - and 6 hex characters, so they never collide with the pi folders curator and plugins.
  15. A change to the data folder's shape raises DATA_VERSION with a step, in the same release.
  16. -ne stays, and PI_BUILTINS names every pi built-in extension when pi is updated.
  17. Pi's RPC lines are split on LF only.
  18. fetch_knowledge never takes a path; its results stay wrapped as background. Notes and vault lines pass unsafe().
  19. Agent-written HTML runs only in the sandboxed frame; downloads keep Content-Security-Policy: sandbox; the app keeps frame-ancestors 'none'.
  20. Chromium never gets a debugging port; the screen's socket and cookie stay user 1000's.
  21. The port stays published on 127.0.0.1; the Host check stays.
