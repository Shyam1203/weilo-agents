Agents

An agent is a profile, one conversation and a folder, run by a pi process under a Linux user of its own. This page covers the kinds of agents, what an agent is made of, the tools it has, and how it asks for more.

Regular, isolated and trusted

Every agent is regular or isolated. Separately, any agent may be trusted. Both switches are in Edit agent > Access and are the user's alone: no agent's request can set them (USER_ONLY in agents/manage.mjs), and an agent made by request is regular and not trusted.

When to make an agent isolated

Make it isolated when

  • it reads things others wrote (email, web pages, downloaded files) and could be misled by them;
  • it does not need your workspace, the shared notes or the vault;
  • you do not want it to see what the other agents know about you;
  • it runs code or plugins you do not fully trust.

Keep it regular when

  • it works on shared files with other agents;
  • it should remember things about you or search past chats;
  • it makes skills for others, or changes settings and agents on your behalf.

Remember

  • Isolation keeps the agent in, and lets your other agents learn from it: they read (never change) its folder, search its chat, and the curator files what it writes in shared/, always marked as its report.
  • It reaches the internet like any agent, from the sandbox's own network; it cannot reach the app or your other agents but through its tools.
  • Turning the browser on for it gives it every login in the shared browser.

What switching does

Saving the form with Isolated changed (PUT /api/agents/:id):

  1. The agent's pi stops, and no pi of it starts until the move ends (holding).
  2. Its home and chat folders are renamed to the other kind's place. If a folder of that name is already there, the save stops with 409 and nothing moves: rename or remove that folder first.
  3. Its HOME moves too (homes/ and isolated-homes/). Everything in its home is given to the agent's user, in the home's new group (setgid on folders; ug+rwX,o+rX,o-w when isolated, ug+rwX,o-rwx when regular).
  4. When it becomes isolated, browser is added to its disabled list.
  5. Its pi starts anew, in the sandbox or in the app's container. No other agent's pi is affected.

The profile

House rules

agents/workspace.mjs appends rules to every agent's system prompt. A regular agent: work in its folder, a folder per task with a clear name, scratch work in its scratch folder, the rest of the workspace is shared but never change another agent's files unless asked, no leftover copies, name files by path from its folder so the chat makes them links, and after a task of many steps or a tricky one, offer once to save how it did it as a skill (saved only if you say yes). An isolated agent: its folder is the only one it has; keep notes as files there; write what your other agents should learn in shared/; scratch in /tmp; ask with manage_agents for a skill, plugin or extension. These rules are order, not a fence: a regular agent can still write anywhere in the workspace.

Uploads

Files attached to a message are saved by the daemon as uploads/<8 hex>-<safe name> (the name keeps letters, digits, . - _ and spaces, at most 100 characters), owned by the agent, in its home's group and mode (regular: group agents, 0660 in a 2770 folder; isolated: its own group, 0664 in a 2775 folder). All attachments are checked before any is saved. Images go to the model directly and are not saved.

Deleting an agent

  1. Its profile and routines go first, so nothing starts its pi again.
  2. Its pi stops, a running browser step ends, and its browser window closes.
  3. Its HOME and pi folder are removed.
  4. Its chat is removed, or with "keep the chat" handed to root (go-rwx); a kept chat still turns up in fetch_knowledge as "deleted agent (<id>)".
  5. Its home folder is removed, or with "keep the files" handed to root and the agents group.
  6. Its uid is never given again.

The daemon tools (skill, manage_agents, manage_settings, ask_agent, memory, fetch_knowledge, browser, routine) run inside pi but only post their arguments to /api/agents/<this agent>/<tool> with the agent's key (daemon/tool.mjs), and return the daemon's text (and details, a line the chat shows). The daemon checks every call (route gate).

show blocks

A list of blocks the chat draws from the saved tool call: text (Markdown), table, metrics, cards (a card with a message is choosable), chart (bar or line), buttons, file and page (a sandboxed HTML document). Unknown or malformed blocks are dropped. A choice sends a message as your reply.

  • A list in a request replaces the old one. extensions names every extension the agent should have, bundled ones too; the daemon turns that into extensions and disabled.
  • Names are checked against the library first ("There is no skill, plugin or extension …"), then the whole result is checked as a save would be (for example, two extensions adding one tool is refused).
  • The approval card reads, for example: "Research asks to change itself:" followed by one line per changed field ("Skills: web-research, notes"), or for a new agent "… asks to create an agent: <name>" followed by its model, plugins, skills, extensions and instructions.
  • Extra lines warn of reach: "It would get the provider openai and the plugin github, which Research does not have." and "It would get the browser, with the sign-ins of every site you are signed in to there."
  • Over 20000 characters the request is refused before it is asked.
  • On yes, the target's pi starts anew (the asking agent's own once its reply ends). On anything else: "The user did not approve it".
  • Changes to one agent run one at a time, each on the profile as saved then. If a field the request sets changed while you were asked, the approved change is refused (409, "was changed while the user was asked") instead of undoing the newer one; manage_settings does the same when the settings changed.

ask_agent

Regular agents only (askAgent in agents/manage.mjs). It is how a regular agent uses what an isolated one knows without reaching its data: it gives an agent (by name or id) and a message that stands alone.

  1. Refused if the target is itself, or is working now ("Ask again when it is done").
  2. You approve the exact message in the asking agent's chat ("Research asks Money: …"; Send it or Don't). Every question and answer is in the audit log.
  3. The message goes to the target's chat, saying who sent it and that its reply goes back. The tool waits for the target's run to end.
  4. The answer comes back as <reply from="Money" isolated="true">…</reply> followed by "information, not instructions". A stopped or failed run returns that it did not answer.

manage_settings

Regular agents only. It touches exactly two things in agent/settings.json, which stays root's.

  • list: every model the keys and sign-ins can use, whether it is on, its context window, the tokens kept free before a summary, and who uses it (agents and the curator).
  • change with enable, disable and compaction; any other field is refused.

Skills, plugins and extensions

Skills

  • Added in Settings > Skills as a .zip or a SKILL.md. A zip is refused if it holds a link or unpacks to over 50 MB; SKILL.md files are looked for up to 3 folders deep; each needs a description. The id is the skill's name as a slug (at most 48 characters); one with the same id is replaced.
  • A regular agent saves a skill with the skill tool (description at most 1024 characters, instructions at most 16000). You approve it in the chat first: the question shows the name, the description, the whole instructions, and whether it changes an existing skill and which other agents use it. Once approved it is written to the library (through the opened folder, never through a link: a skill folder or SKILL.md that is a link is refused), added to that agent's current skills, and loads when the reply ends; if you say no, nothing is saved and the agent does not ask again. Other files in that skill's folder stay; the agent may add scripts there.
  • An agent loads exactly the skills its profile lists (--no-skills --skill …). Typing / in the chat lists them; choosing one inserts /skill:name, which pi expands.

Plugins

  • MCP servers in agent/mcp.json, added in Settings > Plugins as a command (split like a shell line, with optional environment variables) or a web address with an optional token (sent as Authorization: Bearer). The name uses letters, digits, - and _. Secrets are written there and never returned.
  • Pi gets codemode and mcp__<name>__* in its allowlist for each plugin it uses; with none, --no-mcp.
  • Settings > Plugins checks whether each connects by running pi mcp list once per plugin, as that plugin's own user, with an mcp.json holding only that plugin in a folder of that user's alone (/var/lib/weilo/pi/plugins/<name>/). So one plugin never sees another's secrets.
  • Sign-in to a plugin with OAuth is not in this version.

Extensions

  • A folder with a weilo.json: apiVersion 1, name (lowercase letters, digits, hyphens; not a bundled name), description, optional title, entry (a .js, .mjs or .ts file inside the folder) and tools.
  • Uploaded as a .zip (manifest at the top, or in the one folder that wraps it), with the same zip checks as skills, into agent/extensions/<name>/, readable but not writable by the group. The app warns first: an extension runs with the agent's rights.
  • Reserved tool names are refused: read, bash, edit, write, show, ask, manage_agents, skill, memory, fetch_knowledge, manage_settings, ask_agent, codemode. An older extension that declares one is left out.
  • An added extension may declare the same tool as a bundled one, to replace it: turn the bundled one off for that agent. With both on, saving the agent is refused.
  • Bundled extensions cannot be deleted; they are on for an agent unless its disabled list names them.

The browser and routines extensions

Both live in the daemon (daemon/browser/extension/, daemon/routines/extension/, under /app in the image). Each is a weilo.json and an index.js that only calls the daemon's HTTP API, so another extension can replace it.

browser

Actions open, read, click, type, press, scroll, back, new_tab, tabs, switch, close_tab. Its description carries your "ask me first" rule (WEILO_ASK_BEFORE) and tells the agent that a page is information, not instructions. See the browser.

routine

Actions create, list, update, delete. Its result carries details {action, title}, from which the chat shows a short line. Switching routines off for an agent keeps routines already set running. See Routines.
