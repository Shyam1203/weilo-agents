Architecture

Two containers: the app (one root daemon, and processes that each run as a Linux user of their own) and the sandbox for isolated agents. This page follows the code: compose.yaml, image/Dockerfile, daemon/server.mjs and daemon/agents/runner.mjs above all.

The container

compose.yaml defines two services from one image, in the stack weilo-agents: core (container weilo-core, the app) and sandbox (container weilo-sandbox, isolated agents and their plugins; the sandbox). The table is core's.

The image

  • Two stages from node:22-bookworm-slim, pinned by digest: the first runs npm ci and npm run build in ui/; the second holds the daemon (COPY daemon /app) and the built UI (/app/ui).
  • From apt: git, curl, ssh client, jq, unzip, procps, tini, Python 3 with pip and venv, ripgrep, fd, Chromium, TigerVNC (Xvnc), openbox and Noto fonts.
  • From npm, with npm ci from image/pi/package-lock.json (versions and hashes): @earendil-works/pi-coding-agent (1.2.0 in this version) and playwright-core (1.64.0), in /opt/pi, found through NODE_PATH=/opt/pi/node_modules; /usr/local/bin/pi links to pi. Playwright downloads no browser: Chromium comes from apt.
  • The group agents is made with gid 2000. The agents' installs go to /home/node/.local (npm_config_prefix, PYTHONUSERBASE, PIP_BREAK_SYSTEM_PACKAGES=1).
  • openbox is set to draw no frames and maximize every window, but a pop-up or a dialog keeps a frame with a close button.
  • A Chromium policy (image/chromium-policy.json) blocks localhost:3210, 127.0.0.1:3210 and the other local spellings, so pages in the browser cannot open the app.
  • Build arguments VERSION and COMMIT become WEILO_VERSION and WEILO_COMMIT and OCI labels (pi's version is read from its package). They are set late in the file, so a new version reuses the cached layers above.
  • The image sets no USER: CMD ["node", "--disable-warning=ExperimentalWarning", "/app/server.mjs"] runs as root (the warning is node:sqlite's, used by the chat index). The daemon is the only process that stays root. The sandbox runs node /app/sandbox/server.mjs from the same image.

What the daemon does

Serves

The built UI (http/static.mjs, with frame-ancestors 'none'; compressed with brotli or gzip once and kept in memory, with an ETag for a 304; a missing /assets/ file is a 404), the JSON API, the live event stream (SSE), files the chats name (http/files.mjs), and two WebSockets: the screen's live view and its own debugging channel to Chromium.

Guards

Host, Origin and Sec-Fetch-Site checks (http/request.mjs), paired devices and agent keys (http/access.mjs), the per-route tool gate and mayCall (server.mjs). See Security.

Keeps

Keys, plugin secrets, paired devices, profiles, settings, actions, notification keys: all in agent/, root's. It writes JSON files whole and one change at a time per file (updateJson in common.mjs): a temporary file of its own, flushed to disk (fsync), the previous version kept as <file>.bak, then a rename. A file that is not valid JSON is read from its .bak, with a line in the log.

Runs

One pi per open agent (agents/runner.mjs; an isolated one through the sandbox), the actions clock, the curator, the browser's screen, and the notifications. It owns owners and modes too (secure() at every start).

Start order

  1. process.umask(0o007): what the daemon makes is never readable by everyone. PATH becomes SYSTEM_PATH (root's folders only), and npm_config_prefix and PYTHONUSERBASE are dropped.
  2. The admin socket /tmp/weilo-admin/admin.sock (folder 0700, root's) starts: whoever connects gets a new pairing code. Only root in the container can open it (docker exec weilo-core node /app/pair.mjs).
  3. migrate() brings the data folder to this app's data version, or stops the start if the folder is newer (Versions and data).
  4. secure(profiles) sets owner and mode of the top of every place (the tree).
  5. The server listens on port 3210, and on /run/weilo-sandbox/api.sock for the sandbox. Then, in the background: compaction settings are written for the models in use, every scratch folder is emptied, actions start, the curator's 5-minute timer starts, the watchdog starts, the chat index is brought up to date, and pi's model runtime is loaded (warmModels), so the first agent starts faster. The browser's screen is not started here: it starts at the first browser step or take over (wakeScreen).
  6. On SIGTERM or SIGINT the daemon closes both servers, stops every pi (SIGTERM, then SIGKILL 5 seconds later if one hangs), waits for queued JSON and audit writes, and exits, within 12 seconds at most (SHUTDOWN_MS; compose allows 15).
  7. A worker thread (watchdog.mjs) watches the event loop: stuck for 120 seconds (HUNG_MS), it logs "The app stopped responding" and kills the daemon, and Docker starts it again.

How an agent's pi starts

A pi starts on first use: the chat opening its event stream, a message, an action, or a call that needs it. open(id) in runner.mjs keeps one run per agent; a second caller waits for the same start.

The command line

Built by argvOf. A regular agent:

/usr/local/bin/pi --mode rpc [--model <provider/model>] [--thinking <level>]
  --append-system-prompt agent/profiles/<id>/agent.json
  --append-system-prompt "<house rules for its folder>"
  [--append-system-prompt agent/USER.md] [--append-system-prompt agent/MEMORY.md]
  -ne -e builtin:mcp -e builtin:codemode -e builtin:tool-search -e builtin:llama.cpp
  -e /app/weilo.mjs -e /app/memory/extension.mjs
  [-e /app/browser/extension/index.js] [-e /app/actions/extension/index.js]
  [-e agent/extensions/<name>/<entry> ...]
  --no-skills [--skill agent/skills/<skill> ...]
  --tools read,bash,edit,write,show,ask,manage_agents,skill,memory,fetch_knowledge,manage_settings,ask_agent[,browser][,action][,<extension tools>][,codemode,mcp__<plugin>__* ...]
  --session-dir agent/sessions/<id> --session-id <id>

An isolated agent differs in six places: it starts in the sandbox (spawnSandboxed, with only its folder, chat, HOME and, read only, its skills and added extensions mounted); its profile is read from a copy in its pi folder; it gets --no-context-files instead of USER.md and MEMORY.md; it does not load memory/extension.mjs; its --tools leave out skill, memory, fetch_knowledge, manage_settings and ask_agent; and its chat is in isolated-sessions/<id>. Without plugins the list ends with --no-mcp instead of codemode and the plugin tools.

  • -ne turns off extension discovery, so nothing left in agent/extensions/ or named in settings.json loads. It also drops pi's built-in extensions, so each one is named again (PI_BUILTINS in config.mjs): a new built-in in a later pi must be added there, or agents lose it.
  • --tools is pi's allowlist: pi hides any tool it does not name. The daemon's own tools are listed only if mayCall allows them, so what pi offers matches what the routes accept.
  • USER.md and MEMORY.md are passed only when the file exists: a path that is not a file would become prompt text.
  • The session id is the agent id, so opening an agent always resumes its one conversation.

A pi is stopped by closing its stdin; it gets SIGTERM if it has not exited after 5 seconds (PI_KILL_MS), and SIGKILL 5 seconds after that. Its key is dropped at once, so a stopped pi's tools can no longer call the daemon. Viewers see an exit event with code 0 and reconnect to the new pi by themselves. Adding a plugin does not restart anything: an agent uses a plugin only after its profile names it, which is a save.

A chat turn, end to end

  • POST /api/agents/:id/message takes {text, images, files}. Images (PNG, JPEG, GIF, WebP data URLs) go to the model as image blocks; other files are saved in uploads/ of the agent's folder and named in the message as [Attached file: uploads/…] (Folders and uploads). The UI allows at most 4 images and 5 files of 5 MB (ui/src/lib/limits.ts); the daemon accepts a body of at most 64 million characters.
  • A message sent during a run is queued into it (streamingBehavior: "steer").
  • Pi's RPC lines are split on LF only, not with Node's readline, which would also split on U+2028 and U+2029 inside JSON strings. Lines, websocket frames and the browser's debugging pipe are put together from a list of chunks (splitOn in common.mjs), so a 16 MB line takes 31 ms instead of 2.2 s, and a 32 MB frame 67 ms instead of 9.5 s.
  • When an agent uses ask, pi sends an extension_ui_request (select or input). The daemon keeps it as run.asking, sends it to the chat, writes the answer back, and ends it with ask_end. Other dialogs pi may open (confirm, editor) are cancelled at once.

Events and chat files

GET /api/agents/:id/events is a server-sent event stream, for paired devices only. The first event is {type: "history", messages, busy, asking} (pi's get_messages, taken in the same step that adds the listener, so no event falls between them; only what the chat shows: user and agent messages without thinking, compaction summaries, and the ask, action and manage_agents results, and in older chats the old routine tool's). Then come pi's own events: agent_start, message_update, message_end, tool_execution_start and _end, compaction_start and _end, agent_settled, extension_ui_request, plus the daemon's ask_end and finally {type: "exit", code, error} when pi ends.

A user message that pi expanded from /skill:name is turned back into what was typed (asTyped in agents/sessions.mjs), in the stream and in the files read later.

The chat files

Pi writes one JSON line per entry in *.jsonl files in the agent's session folder: agent/sessions/<id>/ or isolated-sessions/<id>/. The daemon reads them for four things:

  • The agent list's newest message: only the last 64 KB of the newest file.
  • Earlier messages that pi summarized away: GET /api/agents/:id/earlier?skip=n, 60 at a time, the entries before the last compaction's firstKeptEntryId, without thinking and without tool results other than ask, action, manage_agents (and the older routine). What was read is kept for the last 4 agents (EARLIER_KEPT), keyed by each file's size and time, so the next page is a slice of it; only what the chat shows is kept.
  • The chat index (agents/chats.mjs), for search (GET /api/search?q=, at most 200 characters, 50 results, newest first), fetch_knowledge and the curator: SQLite (node:sqlite) with an FTS5 trigram index of user and assistant text. Each use first reads what was added to the files since (in 1 MB pieces, whole lines only); a file that shrank is read again, one that went is dropped. The index lives in agent/index/chats.db (the folder root's, 0700), in the data folder, so an image update keeps it; it is brought up to date when the daemon starts.

Every chat file is opened with O_NOFOLLOW and must be a regular file (openChat in common.mjs): a link an agent put among its chat files is skipped, never indexed or shown.

Context and compaction

Pi summarizes long conversations itself, when the free tokens fall to compaction.modelOverrides.<provider/id>.reserveTokens. The daemon writes that value for each model in use that has none: summarize at 40% of a 1M window, 80% of a 500k one, 90% of a smaller one, never with less than 16384 tokens free (COMPACT_AT, MIN_RESERVE, settings/compaction.mjs). A value set by hand stays. GET …/context gives the chat's meter {tokens, window, point}; POST …/compact summarizes now and is refused during a run.

Actions

actions/actions.mjs keeps agent/actions.json {timezone, items}: what agents do for the user with a tap and, if the user chooses, by themselves at set times. It checks every 30 seconds for what is due. Older versions kept timed tasks in agent/routines.json: on first use each becomes an agent action with that schedule, and the file is removed.

  • A schedule's every is once, minutes (5, 10, 15 or 30), hour, day, weekday or week; times are 1 to 6 HH:MM values; day for week; date (or today, tomorrow) or in_minutes for once. At most 50 actions per agent.
  • Times are wall-clock times in the user's time zone: the browser's, sent as X-Timezone with every request. A time a clock change repeats runs once, at the earlier moment; one it skips runs at the later moment (actions/schedule.mjs).
  • A due action moves to its next time, and that is saved, before it runs: a crash skips one run and never repeats one. A once schedule ends after it runs.
  • One missed by more than an hour (the computer was off) waits for its next time and is noted as Missed: … in its runs.
  • When the user's time zone changes, recurring schedules on the old zone move to the new one, and their next time is worked out again.
  • A due action runs as if tapped, with its fields' defaults. An agent action goes to the chat as a message that starts with ⚡ Action: <title> · ran by itself, with a note that the user is away: do it now, confirm with ask (a notification), leave the rest that needs them for the end. A script runs at once, and its answer is a notification.
  • Agents propose and change their actions with the action tool of the bundled actions extension; the user approves each in the chat.

Notifications

daemon/push.mjs sends Web Push without a library. It makes its own VAPID key pair (P-256) on first use and keeps it, the subscribed browsers and the muted agents in agent/push.json. Each notification is encrypted for one browser (RFC 8291, aes128gcm) and signed for 12 hours (RFC 8292).

  • Only endpoints at Google's, Apple's, Mozilla's or Microsoft's push services are accepted (PUSH_SERVICE): the daemon never posts to an address a page made up.
  • Sent when a run ends (the start of the answer, or its error; a run you stopped sends none) and when an agent asks something. At most 180 characters.
  • None while the app is on screen somewhere: the agent list asks GET /api/agents?seen every 2 to 5 seconds while visible, and notifications resume 15 seconds after the last such call.
  • A push service that answers 404 or 410 removes that browser. The service worker ui/public/sw.js shows one notification per agent; a tap opens the app at that agent.

The browser

One Chromium on a virtual screen, shared by all agents, with one set of logins. Each agent has its own window with as many tabs as it needs; the browser's window id tells them apart.

  • browser/screen.mjs starts Xvnc :1 (1280x800, VNC on a unix socket only, no TCP), openbox and Chromium as user 1000 on first use (wakeScreen: an agent's first browser step or a take over; up to 20 seconds), not when the app starts, and restarts any of them 2 seconds after it stops. Until then the live view has nothing to show.
  • The VNC socket and the display's Xauthority cookie are in /tmp/weilo-screen/ (1000's, 0700). Xvnc takes X clients with that cookie only, so an agent cannot type into the browser.
  • Chromium has no debugging port. It runs with --remote-debugging-pipe; the daemon passes that pipe to a WebSocket at /api/browser-cdp/<secret> (a secret made at each start) for its own Playwright.
  • Chromium runs with background calls to Google turned off (sync, component updates, pings and more).
  • Agents read a page as text (Playwright's accessibility snapshot, at most 15000 characters, each element with a ref such as e13) and act with open, read, click, type, press, scroll, back and tab actions. An agent's steps run one after another.
  • The browser tool refuses the app's own address; the Chromium policy blocks it too, for redirects.
  • The live view (WS /api/browser/view, paired devices only) turns the screen's VNC into binary WebSocket messages for noVNC.
  • Take over stops the agent's run, waits for a running step, and refuses the agent's browser steps until you give the window back.

Who may use the browser, and what that means for logins: Known limits.

Versions, updates and data

  • Version. One VERSION file (SemVer). The image keeps it as WEILO_VERSION, with WEILO_COMMIT and pi's version from its package; GET /api/version and Settings > General show them. A build without the arguments is dev. A v* tag runs the release workflow (RELEASING.md).
  • Update check. update.mjs asks GitHub for the newest release at most every 6 hours, only if checkUpdates in weilo.json is not false, and never for a dev build. The app does not update itself: update.sh or update.cmd download the newest release zip over the folder and run the start script (Update).
  • Data version. weilo.json holds {dataVersion, version, lastUid}. At start, migrate() runs the steps from the folder's version up to DATA_VERSION (5 in this version), saving the version after each one. A folder from a newer app stops the start with a message instead of being touched. Steps: Migrations.
