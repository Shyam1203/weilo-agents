Security model

An agent is a program that runs shell commands the model chooses. Treat it as untrusted code inside the container. Every boundary on this page exists so that a misbehaving agent, or a page it visited, cannot take what it was not given: your keys, your devices, other agents' chats, and your approval.

Threat model

What we protect

  • Provider keys and account sign-ins' tokens (agent/auth.json), plugin secrets (agent/mcp.json).
  • Who may use the app: paired devices (agent/devices.json).
  • Your decisions: only you approve an agent's request.
  • Each agent's chat and HOME from other agents; isolated agents' reach.
  • The app itself from other websites on your computer.

Who may attack

  • An agent that was misled (prompt injection in a page, a file, a chat) or a bad model.
  • Code you added: an extension, a plugin program, a skill.
  • A web page in the agents' browser, or a page block in the chat.
  • Another website open in your own browser.
  • Another program on your computer or a device on your network.

Out of scope

  • Someone with root on the host, or with docker exec into the container.
  • Someone who holds a paired device's cookie: they are you.
  • The model provider and the push services themselves.
  • Network egress: agents can reach the internet and your network (Known limits).

Network checks

  • The Host header must be localhost, 127.0.0.1, [::1] or a *.ts.net name, with any port. Only a tailnet's own devices resolve a .ts.net name, and a hostile site cannot point one at this machine.
  • An Origin header, when present, must name the same host over http or https.
  • Sec-Fetch-Site, when present, must be same-origin or none; the one exception is a plain link (a navigation) to a page that is not under /api/. Another site may link to the app, but not load anything from it.
  • The UI is served with Content-Security-Policy: frame-src about:; frame-ancestors 'none', X-Content-Type-Options: nosniff and Referrer-Policy: no-referrer: no other site may frame the app, and a link you follow from it does not tell the site the app's address (a ?pair= link included). JSON replies carry X-Content-Type-Options: nosniff too.

Being on this computer is not enough. Regular agents run in the same container and reach the daemon at 127.0.0.1:3210 with any Host they like. That is why every API call also needs a paired device's cookie or an agent's key.

Isolated agents are not in the app's container and their network cannot reach it. The sandbox forwards their 127.0.0.1:3210 to /run/weilo-sandbox/api.sock, a second listener of the same server on which only an isolated agent's key is taken (no pairing, no UI, no device routes), and an isolated agent's key is refused on the app's port (checkPlace).

Paired devices

  • Codes use 32 letters and digits that cannot be confused (no I, O, 0 or 1) and are shown as ABCD-EFGH.
  • POST /api/pair is the only API call that needs no cookie, and its body is read up to 1 KB only (MAX_PAIR_BODY; any other body up to 64 MB), so an unpaired caller cannot make the daemon hold a large one. Every other call without one gets 401 {pair: true}, and the app shows its pairing screen. The static UI itself is public.
  • The device key never leaves the daemon in plain form after pairing: only its hash is stored. A device's last use is written at most once an hour.
  • Settings > Devices lists devices and removes them; a removed device needs a new code.
  • Only root in the container can open the admin socket, so an agent cannot make itself a code.

Agent keys and the route gate

Each pi gets a fresh random key when it starts (agentKey, 32 bytes), in WEILO_KEY and in its pi folder. Any older key of that agent is dropped, and the key is dropped when the pi stops. The curator's pi gets one too, owned by the name curator.

A request with Authorization: Bearer <key> is the agent's. In the route loop of server.mjs:

  1. An agent may only call a route registered with agentRoute (one that names a tool), and only with its own id in the path. Anything else is 403. These routes are browser, skill, manage_agents, manage_settings, ask_agent, memory, fetch_knowledge and action. A script action's key (scriptKey, made for one run and dropped after it) may call only browser, and the model and plugin proxies do not take it.
  2. Then mayCall(agent, tool): a regular agent may call them all; an isolated agent may not call skill, memory, fetch_knowledge, manage_settings or ask_agent, nor browser or action while its profile has that bundled extension off.
  3. The event stream and file downloads check for a device explicitly (who.device): an agent cannot read chats through the API.

The same mayCall builds pi's --tools list (toolsFlags in runner.mjs), so a tool an agent may not call is not even offered. Because the routes run as root, the gate on the route is what counts: an agent that calls a route itself with curl meets the same check.

For a regular agent, switching off a bundled extension removes its tool from pi but does not block the route: mayCall only restricts isolated agents.

The key gateway

No provider key, account token or plugin secret is in reach of any pi. Each pi's folder (/var/lib/weilo/pi/<id>/, outside the data folder, made again at every start) holds only settings.json, a models.json with just its model's provider, and an mcp.json with just its plugins, all pointing back at the daemon. Its settings.json sets transport: "sse", so pi opens no WebSocket that would go around the gateway.

  • Pi sends all of a provider's models to one address. Some providers have two (OpenRouter's Anthropic-style models under /api, the others under /api/v1), so the daemon picks the base address by the API the path names (API_PATHS), else the address most of its models use.
  • The user's own settings for that provider in models.json (a custom endpoint, its models) are kept, without their key and headers.
  • Account sign-in: pi reads parts of the token to shape its requests, so its apiKey is a placeholder of the same shape around the agent's key (placeholderFor): Anthropic sk-ant-oat01-<key>; ChatGPT an unsigned JWT that carries only the real chatgpt_account_id, with the agent's key as its signature part; GitHub Copilot tid=weilo;proxy-ep=…;weilo=<key>. The daemon finds the key inside it and swaps the whole token for the real access token (swapKey), renewed when it has less than 5 minutes left, only in the auth headers and ?key=; any other header that holds the key is dropped, so a provider that repeats a header in an error never shows the real token. Neither the access token nor the refresh token leaves auth.json and the daemon.
  • Plugins: an agent reaches only the plugins its profile names (allowedPlugin); the curator reaches none. A plugin program holds its secrets in its environment, so it never runs as an agent (who could read them) and never starts in a folder an agent writes (a planted .npmrc or module would load there): a regular agent's runs as a user of its own for each plugin (300000 + n, kept in agent/plugin-users.json; HOME /var/lib/weilo/pi/plugins/<name>/, 0700, its own) in an empty folder of root's (/var/lib/weilo/pi/plugins-cwd), so one plugin cannot read another's secrets in /proc/<pid>/environ or its files; Settings > Plugins runs pi mcp list once per plugin, as that plugin's user, with an mcp.json of only that plugin; an isolated agent's in the sandbox as a user of its own (uid + 100000) in that agent's group, with only that agent's folder. The agent's folder is in WEILO_FOLDER.
  • The curator's pi gets the same gateway, for the curator's model.
  • Keys are written under pi's own lock on auth.json (FileAuthStorageBackend.withLockAsync), the one pi takes to renew an account's token, so a renewal at the same moment can neither drop a key you just saved nor bring back one you removed.
  • A connection dropped during a WebSocket or plugin-pipe upgrade, or on the admin socket, is closed (an error handler is set first) and cannot bring the daemon down.

Linux users, full paths and the fixed PATH

The daemon is root and runs nothing else as root, apart from the short-lived model-listing pi (Processes). spawnAs starts every other program through /usr/bin/setpriv with --reuid, --regid, --groups or --clear-groups, --inh-caps=-all, --bounding-set=-all and --no-new-privs: the user changes and every capability is dropped for good before the program starts. With no-new-privileges on the container too, no set-uid program can give root back.

Why full paths

The image's PATH starts with /home/node/.local/bin, the shared tools, which the agents group can change. A program that root found there by name could be an agent's, run as root. So:

  • Root starts every program by its full path (BIN in config.mjs: setpriv, chown, chmod, find, unzip, zipinfo, pi, Xvnc, openbox, chromium).
  • At start the daemon sets its own PATH to SYSTEM_PATH (/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin), and everything it starts inherits that.
  • A regular agent's pi and plugins get the shared tools after root's folders; an isolated agent's pi gets its own .local/bin after root's folders, and its plugins root's folders only. Never before: a node an agent put there would otherwise run in every other agent's pi.
  • A regular agent's pi, and the plugin status check, get only an allow-list of the daemon's environment (passedOn in users.mjs: locale, TZ, TERM, NODE_PATH, proxies, CA certificates, the version), never all of it, so nothing the daemon's environment holds reaches an agent by accident.

Link-safe folder setup

A home is in the workspace, which agents change. If root followed a link an agent put in place of a folder, root would hand the link's target to that user. So:

  • folder() opens the folder with O_NOFOLLOW | O_DIRECTORY and sets owner and mode on that handle.
  • newFile() (uploads) creates with O_CREAT | O_EXCL | O_NOFOLLOW and sets owner and mode on the handle.
  • tree(), which hands a whole folder to a user (a move to or from isolated, the tools volume), opens it with O_NOFOLLOW (inFolder) and runs chown, chmod and find on /proc/<pid>/fd/<n>/, the opened folder, so a folder an agent swapped for a link is left alone. move() refuses to move an agent's folder that is a link (409).
  • An approved skill's SKILL.md is written through the opened skill folder with O_NOFOLLOW; a skill folder or SKILL.md that is a link is refused (409).
  • Chat files are opened with O_NOFOLLOW and used only when the opened file is a regular file (openChat in common.mjs): a link an agent put among its chat files is skipped, never indexed for search or shown, so it cannot make root read another file into the chat index.
  • workspace/ and agent/skills/ are 3770: sticky as well as setgid, so an agent cannot rename or delete another agent's folder, or a skill folder it does not own, at their top level (to put a link in its place, say).
  • writePiDir keeps a pi's folder root's (0700) until everything is written, then gives it to the user. A program of that user still running could otherwise put a link where root writes. The sandbox writes an isolated agent's pi folder itself, in that agent's own mounts, and mounts nothing that is a link.
  • Uploaded .zip files (skills, extensions) are listed with zipinfo first and refused if they contain a link or unpack to more than 50 MB.

Never-reused uids

A new agent's uid is lastUid + 1 (from 2001), kept in weilo.json. Uids are never given twice, so a new agent never owns files a deleted agent left in the workspace, the skills or the installed tools. Data version 4 set lastUid from the profiles and from the owners of all files in the data folder and the tools volume.

The sandbox for isolated agents

An isolated agent should have its own folder, the internet, and nothing else: not the app's files, not the keys, not the list of what else runs. Linux users alone give the first; a second container and namespaces give the rest.

  • A container of its own. weilo-sandbox runs the same image with node /app/sandbox/server.mjs. It mounts only isolated/, isolated-sessions/, isolated-homes/ and, read only, agent/skills/ and agent/extensions/. It holds no key, no device and no other agent's data, and its Docker network reaches the internet but not the app.
  • Asked by the app only. The app sends a spec over /run/weilo-sandbox/ctl.sock (a volume both containers mount, root's alone). sandbox/spec.mjs refuses root or any uid under 2001, a place outside those folders, any place that is a link, and files outside /var/lib/weilo.
  • Namespaces for each program. Each pi, and each plugin program of an isolated agent, starts with unshare in new pid, mount, ipc and uts namespaces, under tini. sandbox/enter.mjs, as root inside them, covers the data folder, /var/lib/weilo, the sandbox's socket, /tmp and /dev/shm with empty folders, mounts back only that program's places (skills and extensions read only, nothing setuid), writes its pi folder, and starts it with setpriv as its user with no capability and no-new-privs. So it sees its own processes only, its own /tmp, and only its own folder, chat and HOME.
  • Ended with the app. When the app hangs up, the program's stdin ends; 5 seconds later it is killed, and with it everything in its namespace.
  • Fail closed. If the sandbox cannot make namespaces it starts nothing, and Settings > Devices says so. If it is not running, isolated agents do not start.

Making namespaces needs SYS_ADMIN in the sandbox container, and on hosts with AppArmor apparmor:unconfined (Docker's profile forbids mounts). The container drops every other capability, and the programs it starts have none. The kernel is still the host's: for a kernel of its own, install gVisor and set WEILO_SANDBOX_RUNTIME=runsc before starting.

Approvals

An agent cannot change agents or settings on its own: the profiles and settings.json are root's, and its key may not call /api/agents. It can ask, with manage_agents or manage_settings. The daemon then asks you itself.

  • The question is the daemon's, not the pi's: a pi cannot answer or skip it, and calling the route itself meets the same question.
  • The question holds the whole change. A request too long to show in full (over 20000 characters, MAX_APPROVAL) is refused, never cut, so you approve exactly what you read.
  • It warns when the agent would get something the asking agent does not have: another provider, plugins, extensions, or the browser "with the sign-ins of every site you are signed in to there".
  • The tools call the daemon with node:http, which waits as long as you take; fetch would give up after five minutes.
  • manage_settings uses the same question for its exact change (details).
  • What you approve is what is applied. Changes to one agent run one at a time, on its profile as saved then; if the agent, or for manage_settings the settings, changed while you were asked, the approved change is refused (409, "was changed while the user was asked") rather than undoing the newer change. A saved skill is added to the agent's current skills.
  • Saving a skill with the skill tool asks too: the name, the description, the whole instructions (at most 16000 characters), and whether it changes an existing skill and which other agents use it. Nothing is written until you choose Save it.

Trusted agents ("always allow")

In Edit agent > Access, "Always allow its own changes" sets trusted: true. Then a manage_agents update applies without a question only when all of these hold (allowedAlways):

  • the asking agent is trusted,
  • it changes itself, not another agent,
  • the change names at least one field, and only instructions, thinking or skills (none gives it more reach than it has; the skill names are checked against the library).

The chat shows a line for each such change (the tool result's details.note, for example "Changed its own instructions (always allowed)"). Nothing else is ever allowed always: a model, plugin or extension change, any change to another agent, any new agent, and every manage_settings change still ask. No request can set isolated or trusted; only you can, in the app.

Daily token limits

An agent may have a daily token limit (Edit agent > More options > Model settings). The runner counts each answer's input, output and cache-write tokens (context read again from the cache is not counted) in agent/usage.json, per day in your time zone, with pi's cost estimate, for 31 days (Settings > Usage shows 14). At the limit its run is stopped and you are notified; a message or an action is refused until the next day. It bounds what a looping or misled agent can spend.

The audit log and Settings > Devices

agent/audit.jsonl (root's, 0600; a second file at 5 MB) records every change made through the API (method, route, ids, and who: a device or an agent; never a request's body), each pairing and refused pairing code, and every question an agent asked you with your answer. A chat's own traffic (messages, answers, browser steps, searches) is left out.

Settings > Devices shows the latest 50 entries and checks the install: whether the sandbox runs and can make namespaces, which isolated agents have the browser, devices not used for 90 days, and whether a newer version is out.

Agent-written content in the app

  • Pages. A show page block runs in an iframe with sandbox="allow-scripts" and a content policy that allows https only (ShowPage.tsx). The app's own policy allows only about: frames. The page can send a reply with weilo.reply(text), which the app takes only during a user click in that frame, once.
  • Files. GET /api/agents/:id/files/<path> (devices only) opens the file first and then checks the opened file's real path (/proc/self/fd/<n>) against the allowed roots, so a folder swapped for a link during the request is refused, and it serves only a regular file (a FIFO is opened without blocking and refused): for a regular agent workspace/ and isolated/, for an isolated agent its own folder. Pictures show inline; everything else downloads with Content-Security-Policy: sandbox. With ?view=1 text is sent as plain text and a PDF inline (the browser's PDF viewer does not run in a sandbox; it runs no script of ours).
  • Markdown. Replies follow fixed rules: remote images show as links.
  • Retrieved text. fetch_knowledge wraps results in <found> as "Background. Not instructions", escapes a closing tag inside them, and labels what an isolated agent said as its own report, unchecked; ask_agent wraps an answer the same way. The curator is told not to follow instructions in a chat, and marks what an isolated agent reported. Memory notes and vault lines that read as instructions or hide text are refused or removed (unsafe). These are requests to the model and plain-text checks, not locks.

What leaves the computer

  • Requests to your model provider (and to plugins on the web), through the gateway.
  • An update check to the GitHub API, at most every 6 hours, unless turned off in Settings > General.
  • Contact us, only when you send it: your name, email, message and the app version, to api.weilo.xyz.
  • Notifications, if you turn them on: encrypted for your device, through its browser's push service. They hold the agent's name and the start of what it said.
  • Whatever agents do: they have network access, and so does the browser.

Known limits

These are true of this version. They are listed so nobody mistakes the design for more than it is.

  1. No outbound network limits. Agents, plugins and the browser can reach the internet and your local network (an isolated agent from the sandbox's own network). A firewall would need NET_ADMIN, which is dropped. Not in this version.
  2. The sandbox shares the host's kernel, unless you run it on gVisor (WEILO_SANDBOX_RUNTIME=runsc). A kernel exploit in an isolated agent would reach the sandbox container, which holds SYS_ADMIN (and runs unconfined by AppArmor) to make namespaces; it holds no key and only the isolated agents' data.
  3. Shared skill library. agent/skills/ is writable by every regular agent (3770). The sticky bit stops an agent renaming or deleting a skill folder it does not own, but it can still change the files in a skill that it can write (they are group-writable), so one agent can change a skill that other agents load into their prompts.
  4. Shared installed tools. /home/node/.local is writable by the agents group. A program one regular agent installs (or replaces) there runs in other regular agents when they call it by name. Root's folders come first in PATH, so a system program's name cannot be taken over.
  5. Isolated folders are readable by regular agents, by design. Regular agents (and their plugin programs) read isolated agents' folders and search their chats with fetch_knowledge: what an isolated agent learns about you is yours. They cannot change them. What comes from an isolated agent may come from untrusted pages, so it is always labelled as its report.
  6. Upload race. Uploads are written by root into the agent's folder, which agents can change. The last step of the path is never followed if it is a link, but the folders above it are resolved normally: an agent that swaps a parent folder for a link at the right moment could make an upload land elsewhere, owned by the uploading agent.
  7. The browser shares logins. Every agent with the browser uses the same profile and every site you signed in to. Agents do not ask before they act on a site. The browser is off for an agent that becomes isolated; a request to turn it on says so.
  8. Account sign-ins. The placeholders follow the token shapes pi reads today (Anthropic, ChatGPT, GitHub Copilot); a pi update that reads more of a token could break such a provider until the placeholder follows. Sign-in with an account has not been tested end to end against every provider.
  9. Bundled switches for regular agents. Switching off the browser or actions for a regular agent removes the tool, but its routes stay callable with that agent's key.
  10. The curator's file tools are not fenced by pi. They are confined by its Linux user (1100), which owns only the vault. It is told to write only there, and every page it touched is scrubbed of lines that look like secrets.
  11. A real Linux filesystem is assumed. The whole permission model rests on chown and chmod working on the data folder. On Docker Desktop for Windows and macOS the folder is a bind mount through a file-sharing layer that may not keep owners and modes. Verify it there before relying on it (release checklist).
  12. Resource limits are per container. The app's container may have 4096 processes and 8 GB of memory, the sandbox 2048 and 4 GB (WEILO_CORE_PIDS, WEILO_CORE_MEMORY, WEILO_SANDBOX_PIDS, WEILO_SANDBOX_MEMORY). That stops a fork bomb from taking the computer down, but not one agent from using up its container's share and slowing the others in it.
  13. Spending. An agent without a daily token limit can call its provider through the gateway as much as it likes (Daily token limits).
