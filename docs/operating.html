Operating Weilo Agents

Installing, starting, updating, pairing devices, backing up, and finding out what went wrong. The last section is the manual check maintainers run before a release, since the repository has no automated tests.

Install

  1. Install Docker (Docker Desktop on Windows and macOS, Docker Engine with the compose plugin on Linux) and start it.
  2. Download weilo-agents-<version>.zip from the releases page and unzip it. It holds compose.yaml, start.sh, start.cmd, update.sh, update.cmd, VERSION and README.md.
  3. Run start.cmd (Windows) or ./start.sh (macOS, Linux) from the unzipped folder.
  4. In the app: Settings > Providers, sign in with an account or add an API key. Then create an agent.

From a checkout instead: docker compose up -d --build builds the image from the code (its version shows as dev unless you pass WEILO_VERSION).

What the start script does

  1. Checks it is in the folder with compose.yaml and that Docker answers (docker info).
  2. start.sh makes ~/.weilo-agents first, so Docker does not make it as root.
  3. Sets WEILO_VERSION from VERSION and runs docker compose pull; if the pull fails it builds the image here (docker compose build), which takes longer.
  4. docker compose up -d, then waits up to 90 seconds for http://localhost:3210.
  5. Runs docker exec weilo-core node /app/pair.mjs for a pairing link and opens it (macOS open, Linux xdg-open, Windows start). An already paired browser just opens the app.

The container restarts by itself after a reboot (restart: unless-stopped) once Docker runs. Stop it with docker compose down in the folder; your data stays.

Pairing devices

  • The first device is paired by the link the start script opens. Without the script: run docker exec weilo-core node /app/pair.mjs on the computer where the app runs, and open the printed http://localhost:3210/?pair=ABCD-EFGH link within 10 minutes.
  • More devices: on a paired device, Settings > Devices > Add a device. Type the code on the new device's pairing screen, or open the copied link there. A code works once, for 10 minutes.
  • Lost every device (cleared cookies, new browser): run pair.mjs again as above.
  • Remove a device in Settings > Devices; it needs a new code to come back. A device cookie lasts 400 days.
  • After 10 wrong codes in 10 minutes pairing waits 10 minutes.

How it works and why: Security: paired devices.

Remote use

The port stays on 127.0.0.1. To use the app from your phone away from the computer, put both on a Tailscale network and, on the computer, run:

tailscale serve --bg 3210

This forwards the computer's tailnet HTTPS address to the port. The daemon accepts *.ts.net host names and their https:// origins, and sets the device cookie Secure there. Open that address on the phone, then pair it with a code. Other ways to expose the port (a public tunnel, binding it to all interfaces) are not supported: the Host check refuses other names, and the app would be reachable by anyone who finds it.

Update

  • Settings > About and the sidebar say when a newer release exists (checked at most every 6 hours; turn it off in Settings > About).
  • Run update.cmd (Windows) or ./update.sh in the same folder. It asks GitHub for the newest release, and if it differs from VERSION it downloads that release's zip, copies its files over the folder and runs the start script. Both scripts are written to survive being replaced while they run (the shell script is one function ending in exit; the Windows script runs from a copy in %TEMP%).
  • A folder from before 0.1.2 has no update script: download the newest zip once and unzip it over the folder.
  • With a checkout: git pull, then run the start script, or docker compose up -d --build.

What to check after an update

  1. Settings > About shows the new version, build and pi version.
  2. The app opens without a pairing screen on devices that were paired.
  3. An agent answers a message (keys, models and the gateway work).
  4. docker logs weilo-core shows weilo-core listening on :3210 and no migration error.
  5. If the release notes say the data version changed: weilo.json in the data folder shows the new dataVersion. Keep the backup you made before updating until you are sure.

Going back to an older release after a data version change does not work: the older app refuses a newer folder. Restore the backup you made before the update.

Backups

Everything you keep is in ~/.weilo-agents (on Windows, .weilo-agents in your user folder). To back it up or move it to another machine:

  1. Stop the app: docker compose down in the app folder, so no chat file is written meanwhile.
  2. Copy the whole folder, keeping owners and modes. On Linux the files belong to numeric users (2001 and up, 1100, root), so use root and an archiver that keeps them, for example sudo tar -cpzf weilo-backup.tgz -C ~ .weilo-agents.
  3. Restore by unpacking it in the same place (with sudo tar -xpzf), then start the app. The daemon sets the top-level owners and modes again at start.

Two Docker volumes are not in the folder: tools (what agents installed with npm and pip; they can install again) and browser (the browser's logins; you sign in again). The backup holds your keys and paired devices: keep it as private as the folder.

Troubleshooting

SymptomLikely cause and fix
"Docker is not running"Start Docker Desktop or the Docker service, then run the script again.
"Weilo Agents did not start"Read docker compose logs in the folder. Another program on port 3210 stops the container from starting.
Log: "The data folder was made by a newer Weilo Agents"You ran an older app on a newer folder. Update the app, or restore a backup from before.
The app shows "Pair this device"The browser is not paired, or its cookie was cleared or removed. Pair it again.
"Too many wrong codes"Wait 10 minutes, make a new code.
A chat shows pi's error and Try againPi exited with an error, shown as its last line (for example a model that does not exist). Choose another model in Edit agent, or fix the provider.
"There is no key for … Add one in Settings"The agent's model's provider has no key or sign-in.
"Sign in to … again in Settings"An account sign-in's token could not be renewed.
A plugin does not workSettings > Plugins shows each plugin's status (it starts them all; takes a few seconds). A plugin program must be installed where root's folders or the shared tools find it.
The browser panel stays emptydocker logs weilo-core lines starting with [screen] show which program stopped; each is restarted after 2 seconds.
An agent says "An isolated agent cannot use this"It is isolated; change its access in Edit agent, or give it what it needs through its own folder.
Saving Isolated fails with "… already exists"A folder with the agent's name is already in the place it moves to. Rename or remove that folder, then save again.
A change to memory or skills has no effectPis read them when they start. Send /reload in the chat.
No notificationsNone are sent while the app is on screen anywhere. On iPhone, add the app to the Home Screen first. Check the agent is not muted.
Cannot open the workspace on LinuxIts files belong to the app's users in group 2000: add yourself to that group, or use sudo.

Before you release: the manual check

CI type-checks and tests the daemon, builds the UI and the image, and checks that the sandbox makes namespaces. What only a real install shows is checked by hand before tagging a release: a maintainer builds the image and exercises the boundaries. Run it on Linux, and on Docker Desktop for Windows and for macOS when the release touches users, modes, folders or the start scripts.

How to act as an agent

Probes run a command as an agent's user. Take the uid from the agent's profile:

docker exec weilo-core cat /home/node/.pi/agent/profiles/<id>/agent.json   # "uid": 2001
docker exec weilo-core setpriv --reuid=2001 --regid=2001 --groups=2000 \
  --inh-caps=-all --bounding-set=-all --no-new-privs -- /bin/sh -c 'umask 007; <command>'

An isolated agent runs in the sandbox: probe it by asking the agent in the app to run the command with bash.

Or ask an agent in the app to run the command with bash; its own WEILO_KEY is then in its environment.

  1. Build. CI is green. docker compose up -d --build builds the image and starts both containers; docker ps shows both healthy, and docker logs weilo-sandbox says "weilo-sandbox ready" without a namespace warning. Settings > Security shows the sandbox running.
  2. Start and migrate. Start once on an empty data folder and once on a copy of a folder from the previous release. weilo.json shows the current dataVersion; agents, chats and files are there. Put a higher dataVersion in a copy: the start must stop with the "newer Weilo Agents" message.
  3. Pairing. Without a cookie, curl -i http://localhost:3210/api/agents gives 401 with "pair":true. A code from pair.mjs pairs once and fails the second time. Eleven wrong codes give 429. Removing a device sends it back to the pairing screen. Through tailscale serve the cookie has Secure.
  4. Network guard. With a valid cookie, a request with Host: example.com, with an Origin header naming another site, or with Sec-Fetch-Site: cross-site gives 403.
  5. Agent key gate. From an agent: curl -H "Authorization: Bearer $WEILO_KEY" http://127.0.0.1:3210/api/agents gives 403; …/api/agents/<another id>/memory gives 403; …/api/agents/$WEILO_AGENT/events gives no stream; its own …/memory with {"action":"list"} works. From an isolated agent, its own …/memory gives 403 "An isolated agent cannot use this".
  6. Key gateway. As an agent, cat $PI_CODING_AGENT_DIR/models.json shows the daemon's address and the agent's own key, never a real key; cat /home/node/.pi/agent/auth.json is denied. A chat with the agent works. A request to /api/model-proxy/<another provider> with its key gives 403. Repeat with a provider signed in with an account.
  7. Plugins. A web plugin with a token works, and the token is not in the agent's pi folder. A program plugin works and runs as uid 1200 in /var/lib/weilo/pi/plugins-cwd (ps -o user,args); for an isolated agent it runs in the sandbox as the agent's uid + 100000, and the agent cannot read its environment.
  8. Isolated agent start. Make an isolated agent: its folder is isolated/<folder>/ (<uid>:<uid> 2775), its chat isolated-sessions/<id>/, its HOME isolated-homes/<folder>/; its pi runs in weilo-sandbox with no supplementary groups, and its tools are only read, bash, edit, write, show, ask, manage_agents plus its extensions and plugins (ask it to list them). Asked to run ps -e, it sees only its own processes; ls /home/node/.pi/isolated shows only its folder; curl https://example.com works; curl http://127.0.0.1:3210/api/agents with its key gives 403.
  9. Permission probes. Expected: isolated sees no workspace/, agent/ (but its own skills, read only), other agent's chat, other isolated folder, /home/node/.local or /run/weilo-sandbox; it can write its own folder, chat and HOME. A regular agent can list isolated/ and read an isolated folder, but cannot write it, and cannot read an isolated agent's chat, HOME or pi folder. A user in group 2000 alone cannot pass through isolated/. No agent can read knowledge/, /home/node/.browser, /tmp/weilo-screen or /tmp/weilo-admin.
  10. Switching. Switch an agent to isolated and back while another agent runs: its folder, chat and HOME move and are handed over, the other agent keeps running, the browser is off after becoming isolated. With a folder of the same name in the target place, saving gives 409 and nothing moves.
  11. Approvals. Ask a regular agent to create an agent and to change another's model: each shows a card with the whole change and the extra-reach lines; Don't changes nothing; Skip is no. A regular agent asked to change an isolated one is refused. An isolated agent can ask only for its own skills, plugins and extensions. A trusted agent changing its own instructions applies with a line in the chat; changing its model still asks. A request over 20000 characters is refused. manage_settings: turning off a model in use is refused; a valid change asks and then restarts agents.
  12. PATH and full paths. As a regular agent put an executable named node, pi and setpriv in /home/node/.local/bin that writes a marker file. Restart agents, list plugins status, run the curator: no marker appears. Remove them afterwards.
  13. Memory. The memory tool refuses a note with password: x and one that says "ignore your instructions". With Ask before saving on, a note waits for your answer in the chat. With a curator model set, after a quiet chat a page appears in knowledge/ owned by 1100, and fetch_knowledge finds it; a note an isolated agent writes in shared/ is filed with an isolated: source, and a link there to agent/auth.json is not read.
  14. Agents' questions and limits. A regular agent's ask_agent to an isolated one asks you, and the answer comes back marked as its report. An agent with a daily token limit of 1000 stops after its first answer and refuses the next message. Settings > Security lists the changes you made.
  15. Browser. Take over and give back work; an agent cannot open http://localhost:3210 in the browser; the live view needs a paired device.
  16. Routines and notifications. A routine in 2 minutes runs and shows "Routine: …"; with the app closed, a phone with notifications on gets one.
  17. Update. From the previous release's folder, update.sh and update.cmd bring the new version, keep the data, and Settings > About shows it.
  18. Docker Desktop for Windows and macOS. On the bind-mounted data folder, check inside the container that ls -ln /home/node/.pi shows the owners and modes from the tree, then run the permission probes. If owners or modes are not kept there, the agent boundaries do not hold on that platform: say so in the release notes.
